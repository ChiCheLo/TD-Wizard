## Overview

寶石嵌合是 TD Wizard 的**內容軸**。遊戲只有一種基礎防禦塔——它本身能攻擊
（通用單體攻擊，鎖定第一隻敵人），但沒有屬性、也沒有戰術特色。嵌入寶石後，
塔的攻擊機制、索敵邏輯、攻速與屬性標籤**全部由寶石接管**，該塔隨即特化為
五種戰術角色之一：範圍灼燒、減速場、鏈式跳彈、群體擊退、單體穿甲。

寶石採**實例制**——每顆寶石是獨立物件，各自持有等級。玩家可同時擁有同屬性的
多顆寶石且等級不同，嵌合時需選擇使用哪一顆。這使配置決策分為三層：

```
蓋不蓋塔      → 不受限
特化哪幾座    → 受寶石數量限制
特化到多好    → 受寶石等級限制
```

升級採**融合**：消耗 2 顆同屬性 Lv1 換取 1 顆 Lv2，產生「數量 vs 品質」的取捨。
等級僅提供小幅數值提升，刻意不足以壓過屬性選擇本身。

此系統同時是**連攜系統的前提**——連攜技能以**配方**（所需屬性與固定數量）定義，
巫師範圍內若湊不出配方，該技能無法發動。寶石配置因此不只決定單塔輸出，
更決定玩家能使用哪些連攜技。

## Player Fantasy

> **「我在決定哪些塔值得被賦予力量。」**

塔隨時能蓋，但寶石有限、嵌合要錢。玩家站在防線前，腦中跑的是
「這個轉角值得放我唯一那顆 Lv2 的蝕嗎？還是留給後面那個更窄的路口？」
——每一次嵌合都是在分配稀缺資源。

滿足感來自**看懂局面後做出正確配置**，而非操作技巧。當玩家發現
「霜放入口、蝕放轉角、火放窄道」能清掉一波原本擋不住的敵人，
那一刻的感受是**我想通了**，不是**我反應夠快**。

這直接服務支柱①（配置勝於操作）。寶石系統的每個設計——實例制的稀缺、
索敵內建、嵌合有成本——都在把注意力推向戰前思考。

## Detailed Design

### Core Rules

1. **每座塔有且僅有一個寶石插槽。**
2. **基礎塔（未嵌合）具備攻擊能力**：通用單體攻擊、索敵「第一隻」、基準攻速、
   **無屬性**（不觸發剋制，也不受被剋影響）。
3. **嵌入寶石後，寶石完全接管四項特性**：攻擊機制、索敵邏輯、攻速、屬性標籤。
   基礎攻擊被**取代**，非疊加。
4. **索敵邏輯內建於屬性，玩家不可切換。** 不提供「打最前／最後／最強」的手動設定。
5. **寶石採實例制。** 每顆寶石是獨立物件，各自持有等級。
   可同時擁有同屬性多顆不同等級的寶石。
6. **一顆寶石同時只能嵌在一座塔上。**
7. **嵌合需支付費用 `C`**（關卡內金錢），準備期與戰鬥期同價。
8. **塔被摧毀或主動拆除時，寶石自動回收至庫存。寶石永不損毀。**

#### 基礎塔規格 ⚠️ provisional（待塔系統 GDD 確認）

| 項目 | 值 |
|---|---|
| 攻擊機制 | 通用單體投射物 |
| 索敵 | 第一隻（最接近目標的敵人） |
| 攻速 | 基準值（1.0×，其他屬性以此為比較基準） |
| 屬性 | **無** |

> 基礎塔的定位是**可用但平庸**，同時是**預算選項**——錢少時多蓋幾座基礎塔，
> 錢多時少蓋但嵌好寶石。
>
> 「無屬性」意味著它面對被剋制的敵人時反而穩定（不吃 ×0.75），
> 但也永遠吃不到 ×1.5 的剋制加成。

#### 屬性相剋環

> 📌 **模型變更（2026-09-20，來源：連攜系統設計）**：
> 原版本採「敵人各自持有 `WeakAttribute` / `ResistAttribute`」，
> 兩欄位手寫、互斥、彼此無關聯。現改為**五屬性相剋環**——
> 敵人只持有**一個**屬性欄位，弱點與抗性由環自動推導。
>
> 變更理由：連攜技能會**賦予敵人屬性**（如「炎寒領域」的暴風雪階段賦予霜屬性），
> 需要元素與元素之間的剋制關係。舊模型只有「敵人對某屬性弱」，
> 無法表達「火剋霜」這種元素間的關係。

**環的形狀**（每個屬性剋一個、被一個剋，其餘中立）：

```
        火
      ↗    ↘
    蝕        霜
    ↑         ↓
    風  ←—  雷
```

| 剋制方 | 被剋方 | 直覺 |
|---|---|---|
| 火 | 霜 | 融化 |
| 霜 | 雷 | 冰層絕緣 |
| 雷 | 風 | 雷霆破開氣流 |
| 風 | 蝕 | 吹散鏽塵 |
| 蝕 | 火 | 鏽蝕耗盡燃料 |

**倍率判定**：

| 情況 | `AffinityMult` |
|---|---|
| 攻擊屬性**剋**敵人屬性 | **1.5** |
| 敵人屬性**剋**攻擊屬性 | **0.75** |
| 其餘（含中立組合、無屬性任一方） | **1.0** |

> ✅ **互斥是結構自帶的**：環上任兩個屬性之間至多存在一個方向的剋制關係，
> 因此不可能同時觸發 ×1.5 與 ×0.75。舊模型需要額外寫一條「互斥」規則，新模型不需要。

**敵人的兩個屬性欄位**：

| 欄位 | 說明 |
|---|---|
| `BaseAttribute` | 天生屬性，永久。可為 `null`（無屬性敵人，恆 ×1.0） |
| `AppliedAttribute` | 外力賦予，**有時效**。由連攜技能等效果施加 |

**判定優先序**：`AppliedAttribute` 存在時優先採用；否則採 `BaseAttribute`。

- 賦予的屬性**與天生屬性相同**時：僅刷新時效，無額外效果
  （對應 game-concept §3.2「如怪物本來就是霜屬性則不變」）
- 賦予的屬性**與天生屬性不同**時：在時效內完全覆寫，天生屬性暫不生效
- 時效結束後回歸 `BaseAttribute`

#### 屬性暴露率（第 3 輪審查新增的定案）

> 📌 **澄清**：相剋環對每一次塔攻擊生效——但**舊模型也是如此**
> （`WeakAttribute` 對任何塔攻擊都觸發 ×1.5）。改版改的是**結構**，不是範圍。
>
> 真正改變的是**暴露率的控制權**：舊模型兩個欄位皆可空，設計師能讓大量敵人完全中性；
> 相剋環若不明定，會被誤解成「每隻敵人都必須有屬性」。故在此定案。

**大多數敵人 `BaseAttribute = null`。約三成敵人持有屬性。**

| 敵人類別 | 屬性 |
|---|---|
| 一般小怪（多數） | `null`——恆 ×1.0，不吃剋制也不被剋 |
| 特殊怪、菁英、頭目 | 持有 `BaseAttribute`，符文明示 |

**為什麼**：

1. **屬性成為事件，不是背景噪音。** 玩家看到符文才需要反應；沒符文的就正常打。
   呼應支柱③「輕鬆是底色，高潮是點綴」。
2. **大幅降低死局風險。** 「至少兩種可行屬性解」的驗證規則，
   在多數敵人中性時幾乎自動成立。
3. **讓連攜的「賦予屬性」真正有價值**——把本來沒屬性的敵人染成你剋得動的屬性，
   是憑空創造一個 ×1.5，而非在既有屬性上小幅挪移。

#### 剋制在設計中的定位：調味，不是主菜

> ⚠️ **這一節是為了防止日後重新爭論而寫的。**

第 3 輪審查計算過：若每隻敵人都有屬性，任一屬性的塔面對隨機敵人的期望倍率是

```
20% × 1.5  +  20% × 0.75  +  60% × 1.0  =  1.05
```

**+5%。1.5 與 0.75 幾乎互相抵銷。** 在「大多數敵人無屬性」的定案下更低。

**這是刻意接受的。** 寶石的主要價值**不在倍率，而在完全接管攻擊機制**——
區域燃燒、減速場、鏈式跳彈、群體擊退、單體穿甲。
火寶石吃 ×0.75 打怪群，仍然遠勝基礎塔的單體 ×1.0。倍率只是機制之上的修正項。

相剋環存在的理由是**支撐連攜的染色 combo**（見 game-concept §3.2「炎寒領域」），
不是為了成為日常配置的驅動力。

> 📌 **因此不要為了「讓剋制更有感」而調高 `WeaknessMult`**。
> 1.5 這個值受 `LevelMult` 約束——必須保證「Lv1 打剋制（1.50）＞ Lv2 打被剋（0.90）」
> 且「Lv1 打剋制 ＞ Lv2 中立（1.20）」，動它會破壞「屬性選擇壓過等級」的驗算。

#### 五種寶石規格

| 功能名 | 寶石名 | 色相 | 類型 | 索敵 | 攻擊機制 | 攻速 |
|---|---|---|---|---|---|---|
| **火** | 爐心石 | 橙紅 25° | 區域 | 射程內隨機敵人 | 週期性投放固定範圍燃燒區，持續數秒 | 中 |
| **霜** | 凍泉晶 | 青 190° | 區域 | 射程最前緣（固定） | 持續維持減速場，敵人進入時受一次性傷害 | 持續 |
| **雷** | 鐘鳴石 | 黃 55° | 指向 | 第一隻 → 跳躍 | 鏈式跳彈，4 次跳躍，**可重複命中同一目標**，每跳 −20% | 中 |
| **風** | 風信石 | 綠 130° | 指向 | 最前排數隻 | 群體小幅擊退，**距離隨機**，不疊加 | 快 |
| **蝕** | 鏽紋紫晶 | 紫 285° | 指向 | **固定第一隻，不越位** | 單體重擊，附加穿甲 debuff | 慢 |

**類型分野**：火與霜是**場域型**（放置後持續作用），雷、風、蝕是**指向型**。

**角色不重疊檢查**
```
基礎  → 打「最前面的」，通用無特色
火    → 打「聚在一起的」＊
霜    → 打「剛進場的」，並拖慢
雷    → 打「排成串的」
風    → 打「最前面的」，推回去
蝕    → 打「最前面的」，讓他變脆
```
基礎、風、蝕同樣盯最前排，但基礎是普通輸出、風延後抵達時間、蝕加速死亡。

> ＊ **火的措辭澄清**：火**不做智慧索敵**。它的索敵是「射程內隨機敵人」，
> 投放的是**固定範圍的燃燒區**。「打聚在一起的」描述的是**結果**——
> 敵人越密集，同一塊燃燒區覆蓋到的越多——**不是**它會主動尋找密集處。
> 實作時不得加入任何「找最多敵人的位置」的邏輯。

### States and Transitions

| 狀態 | 說明 | 可轉換至 |
|---|---|---|
| `Empty` | 已建造，未嵌合。使用基礎攻擊 | `Socketed` |
| `Socketed` | 已嵌合，寶石接管所有攻擊特性 | `Empty`（取下）、`Socketed`（替換） |

#### 嵌合經濟模型

只有**單一成本參數 `C`**，階段差異由退款政策產生：

| 操作 | 準備期 | 戰鬥期 |
|---|---|---|
| **嵌入** | 花費 `C` | 花費 `C` |
| **取下** | **全額退還 `C`** → 淨成本 0 | **不退還** → 損失 `C` |
| **替換** | 退舊付新 → 淨成本 0 | 損失舊的 `C` + 付新的 `C` |
| 塔被摧毀 | — | 寶石回收，**嵌入費不退還** |

> **設計意圖**：
> - 準備期實驗仍然免費——可無限次試裝、拆掉、換一顆，淨成本為零
> - 戰鬥期改配置真的痛——除建造硬直的風險外，還會白白損失已投入的錢
> - 塔被摧毀時嵌入費不退還：投資隨載體消失，但寶石本身是可回收資產

> 📌 **`C` 是比例，不是 flat fee。** 第 3 輪審查曾質疑「早期便宜塔金額太小不構成決策、
> 後期昂貴塔金額太大不敢重配」。此質疑的前提不成立——
> **本作只有一種基礎塔**（反支柱②：不做多種塔型），不存在塔的價格階梯；
> 且 `C` 定義為建造費的 60%，本身就是比例。
> 若日後出現任何形式的塔價格分層，本節須重新檢視——但那會先違反反支柱②。

**共通限制**：任何嵌合操作期間，巫師進入**建造硬直**——無法攻擊、無法閃避
（見建造系統 GDD，provisional）。

#### 介面契約 ⚠️ provisional（`/design-review` 修訂新增）

> 📌 上游系統（塔／傷害計算／敵人）皆尚無 GDD。以下型別簽章是本系統對它們的**最小需求**，
> 供撰寫 stub/mock 測試之用；上游 GDD 定案時須回頭核對是否相容，不相容則以上游 GDD 為準並回填本節。

```csharp
// 塔系統須提供
interface ISocketableTower
{
    GemInstance? CurrentGem { get; }       // null = 未嵌合（Empty 狀態）
    bool TrySocket(GemInstance gem);       // false = 槽位已佔用，呼叫前須先 Unsocket
    GemInstance? Unsocket();               // 回傳被取下的寶石，Empty 狀態時回傳 null
    BaseAttackSpec BaseAttack { get; }      // 基礎攻擊規格（單體、索敵第一隻、基準攻速、無屬性）
}

// 傷害計算／連攜系統須提供
GemAttribute? GetTowerAttribute(ISocketableTower tower); // null = 未嵌合（無屬性）

// 敵人系統須提供
interface IAttributeTarget
{
    float Armor { get; }                    // ≥ 0，無甲敵人為 0
    GemAttribute? BaseAttribute { get; }     // 天生屬性。null = 無屬性敵人（多數），恆 ×1.0
    GemAttribute? AppliedAttribute { get; }  // 外力賦予、有時效。判定時優先於 BaseAttribute
    float AppliedAttributeRemaining { get; } // 剩餘時效（秒）。無賦予時為 0
    void ApplyAttribute(GemAttribute attr, float duration); // 連攜技能等效果呼叫

    // 穿甲：以獨立疊加清單持有，非預算好的單一值。
    // 理由：各筆 debuff 時效不同，須能個別到期；EffectiveArmor 於查詢時即時彙總
    IReadOnlyList<PenetrationStack> Penetrations { get; }
    void AddPenetration(float amount, float duration);
}

// 相剋環查詢（傷害計算系統擁有）
bool Counters(GemAttribute attacker, GemAttribute defender); // attacker 是否剋 defender
```

> ⚠️ **`AppliedAttributeRemaining` 是 Visual/Audio Requirements 的硬需求**——
> 「時效將盡時符文加快閃爍」沒有這個查詢就無法實作，連 UI stub 都寫不出來。

> ⚠️ **`Counters()` 為 MVP 專用簽章，預期改動。**
> 它假設單一環、二元關係。v1.0 擴到 12–15 種屬性時，環的形狀無解（見 Open Questions）。
> 屆時此簽章可能需改為回傳倍率而非布林，或接受「環 ID／分組」參數。
> **下游不應假設此簽章穩定。**

`GemAttribute` 為列舉型別，五個值：`Fire`、`Frost`、`Lightning`、`Wind`、`Eclipse`（對應火、霜、雷、風、蝕）。

相剋環為固定常數：`Fire→Frost→Lightning→Wind→Eclipse→Fire`。

#### ⚠️ 對傷害計算系統的硬性契約：批次邊界

本 GDD 有兩條規則預設存在**明確的傷害結算批次邊界**：

| 規則 | 依賴 |
|---|---|
| 火的疊層驅逐「持續重估」 | 需要定義「一次 stack-application 事件」的邊界 |
| 風的擊退「同一次傷害結算批次只套用一次」 | 需要批次內入列、批次結束統一裁決 |

**Unity 的 `Update()` / 物理回呼執行順序不保證確定性。**
若無中央調度器，風的驗收標準「不依賴命中順序、避免同局不同次執行結果不一致」
**是一個實作層無法驗證的自我承諾**。

> **因此傷害計算系統 GDD 必須定義一個中央傷害結算調度器**，
> 明確規範每幀的批次邊界、入列與裁決時機。
> 在該 GDD 存在之前，本系統的火疊層與風擊退**無法寫出可信的 stub**。
>
> 此項已登記於 systems-index §8 傳入約束。

**事件廣播**（透過事件匯流排，見 systems-index §3）
```
OnGemSocketed(tower, gemInstance)
OnGemRemoved(tower, gemInstance, refunded: bool)
OnGemFused(consumedInstances, resultInstance)
OnGemAcquired(gemInstance, isNewType)
OnTowerDestroyed_GemReturned(gemInstance)
```

## Formulas

### 最終傷害

所有攻擊皆經過此公式：

`FinalDamage = BaseDamage × LevelMult × AffinityMult × (1 − ArmorReduction)`

| 變數 | 符號 | 型別 | 範圍 | 說明 |
|---|---|---|---|---|
| 基礎傷害 | `BaseDamage` | float | 待調 | 該屬性的基準傷害 |
| 等級倍率 | `LevelMult` | float | 1.0 / 1.2 | Lv1 = 1.0，Lv2 = 1.2 |
| 剋制倍率 | `AffinityMult` | float | 0.75 / 1.0 / 1.5 | 被剋 / 中立 / 剋制。由**屬性相剋環**推導，見 Detailed Design |
| 護甲減免 | `ArmorReduction` | float | 0–0.75 | 由有效防禦力線性換算，見下方「護甲減免換算」節 |

**輸出範圍**：`0.1875` 倍（Lv1 打被剋且防禦力達 `ArmorReductionCap` 上限：`1.0 × 0.75 × 0.25 = 0.1875`）
至 `1.8` 倍（Lv2 打剋制且無防）。

> 📌 **數值修正（`/design-review` 修訂）**：原版本誤寫為 `0.5625`
> （只算到「高防但非上限防禦力」的中間情況，未推到 `ArmorReductionCap` 的真正下限）。
> `0.1875` 才是理論最小值。

**關鍵驗算**——確保屬性選擇壓過等級：

```
Lv1 打剋制    = 1.0 × 1.5  = 1.50
Lv2 打中立    = 1.2 × 1.0  = 1.20
Lv2 打被剋    = 1.2 × 0.75 = 0.90
```

✅ 用對屬性的 Lv1（1.50）穩穩勝過用錯屬性的 Lv2（0.90），
符合 game-concept §4.1「等級不可輾壓屬性選擇」。

### 有效防禦力（穿甲）

`EffectiveArmor = max(BaseArmor × 0.25, BaseArmor − ΣPenetration)`

| 變數 | 型別 | 範圍 | 說明 |
|---|---|---|---|
| `BaseArmor` | float | ≥ 0 | 敵人原始防禦力 |
| `ΣPenetration` | float | ≥ 0 | 所有生效中的穿甲 debuff 總和（可疊加） |
| 下限係數 | float | 0.25 | **硬性下限**，防禦力永不低於原始的 25% |

**範例**：`BaseArmor = 100`，三座蝕塔各上 30 點穿甲 → `ΣPenetration = 90`

```
max(100 × 0.25, 100 − 90) = max(25, 10) = 25
```

→ 下限生效，防禦力停在 25，多出的穿甲被浪費。**這是刻意的邊際遞減。**

### 護甲減免換算（`EffectiveArmor` → `ArmorReduction`）

> 📌 **本節為 `/design-review` 修訂新增**——原版本只定義了 `ArmorReduction` 的數值範圍
> （0–0.75），未給出換算式，導致 `FinalDamage` 公式無法被實作。

採**線性換算**：

`ArmorReduction = min(ArmorReductionCap, EffectiveArmor / ArmorReductionScale)`

| 變數 | 型別 | 範圍 | 說明 |
|---|---|---|---|
| `EffectiveArmor` | float | ≥ 0 | 見上節 |
| `ArmorReductionScale` | float | **> 0**（硬性約束，見下方），待調（新增 Tuning Knob，符號 `K`） | 防禦力換算為減免比例的除數。`EffectiveArmor = K` 時，減免達到上限 0.75 |
| `ArmorReductionCap` | float | 0.75 | 硬性上限，見 Tuning Knobs |

> ⚠️ **硬性約束（`/design-review` 修訂新增）**：`K` 必須恆為正數（`K > 0`）。
> 若 `K = 0`，`ArmorReduction = EffectiveArmor / K` 將產生除以零。原型實測調整 `K` 時，
> 不可將其設為 0 或負值；此約束須反映在資料驗證（ScriptableObject 欄位下限）中。

**選擇線性而非邊際遞減曲線的理由**：防禦力對玩家而言應像一條直覺可讀的「資源條」——
穿甲每點的邊際效益全部由 `EffectiveArmor` 自身的 25% 下限機制負責遞減
（見上節），`ArmorReduction` 的換算不需要疊加第二層遞減。

**範例**（假設 `K = 200`）：`EffectiveArmor = 25`（即上例下限生效後的結果）
→ `ArmorReduction = min(0.75, 25/200) = 0.125`。

### 雷的跳躍傷害

`JumpDamage(n) = BaseDamage × 0.8ⁿ`，其中 `n` = 跳躍序號（初擊 `n = 0`）

| 跳躍 | 係數 | 傷害 |
|---|---|---|
| 初擊 | 0.8⁰ | 100% |
| 第 1 跳 | 0.8¹ | 80% |
| 第 2 跳 | 0.8² | 64% |
| 第 3 跳 | 0.8³ | 51.2% |
| 第 4 跳 | 0.8⁴ | 41.0% |

**總傷害上限** = 336.2%（全部命中時）。
即使在兩隻敵人間來回彈射，總收益仍收斂於此。

### 風的擊退距離

`KnockbackDistance = BaseKnockback × Random(0.6, 1.4)`

隨機幅度 ±40%。**不疊加**——同一敵人同時被多座風塔命中時，只套用一次擊退。

### 融合

`Lv2 × 1 ← Lv1 × 2`（同屬性）。被消耗的 2 顆實例自庫存移除。

> 📌 **數值修正（`/design-review` 修訂）**：原版本 `FusionCost = 3`，
> 依「Lv1 選對屬性永遠贏 Lv2 選錯屬性」的驗算結果，理性玩家幾乎不會主動融合，
> 且 Open Question #9 估算約 6% 玩家整局遊戲湊不到一次融合材料。
> 調降至 `2` 大幅降低此機率（同屬性配對所需樣本數遠低於三顆），
> 同時仍保留「消耗多顆換一顆」的數量 vs 品質取捨。

#### 融合的取捨驗算

> ⚠️ **此處比較的是玩家實際面對的選擇，不是寶石之間的優劣。**
> 下方「Lv1 選對 1.50 vs Lv2 選錯 0.90」那張表驗證的是**選哪顆寶石嵌合**，
> 與「要不要融合」是兩個不同決策。融合的真正對照組如下。

玩家手上有 2 顆同屬性 Lv1，面對的是：

| 方案 | 產出 | 有效倍率合計 |
|---|---|---|
| **不融合** | 2 座打中剋制的 Lv1 塔 | `1.5 + 1.5 = 3.0` |
| **融合** | 1 座打中剋制的 Lv2 塔 ＋ 1 座無寶石基礎塔 | `1.8 + 1.0 = 2.8` |

> ⚠️ **框架更正（第 3 輪審查）**：原本把 −6.7% 當成主結論、站位稀缺當成例外。
> 這是錯的——**支柱②明定站位是「有限且持續被爭奪的資源」，稀缺才是常態**。
> 以「兩個站位一樣好」為基準去下結論，等於拿最罕見的情況當代表值。
> 以下改以正確的權重陳述。

**常態（站位稀缺）：融合是優勢選項。**
能涵蓋主要路徑的位置有限，第二座塔只能放在覆蓋差的位置，其名目 `1.0` 實際貢獻遠低於此，
融合後集中的 `1.8` 勝出。

**下界（兩個站位一樣好，罕見）：融合是小幅淨損 −6.7%（`2.8` vs `3.0`）。**
這個下界是刻意保留的——它確保融合**不是無腦必做**。
若連最理想的攤開情境都輸，玩家就不會思考，只會照做。

換句話說：**融合在多數情況下該做，但存在一個「攤得開就別融」的反例，
而判斷自己屬於哪一種，就是這個決策的內容。**

其餘勝出情境：

- 能涵蓋主要路徑的優良位置有限，第二座塔只能放在覆蓋差的位置，
  其名目 `1.0` 實際貢獻遠低於此，融合後的 `1.8` 反而勝出
- 面對高防禦力敵人時，`ArmorReduction` 對低單擊傷害的懲罰更重
  （減免是比例制，但分散輸出更容易被 25% 下限以上的護甲吃掉有效傷害），
  集中輸出的邊際效益高於名目倍率所示
- 連攜技的**配方**需要特定屬性的塔時，塔的數量不如塔的屬性正確重要

> **殘留風險**：若原型實測顯示優良站位其實不稀缺（關卡設計過於寬鬆），
> 融合會退化成永遠的劣選。此項併入 Open Question #9 一併驗證。

#### 融合材料的供給驗算（第 3 輪審查要求）

審查質疑「MVP 內融合這個決策是否實際發生得了」。**供給面可以直接證明。**

```
初始      3 顆（3 種各 1）
關卡掉落  GemDropPerLevel(2) × 6 關 = 12 顆
總計      15 顆，其中 12 顆隨機落在 5 種屬性上
```

**鴿籠原理**：12 顆分進 5 格，必然有某格 ≥ 3 顆（因 12 > 5×2）。
融合只需同屬性 2 顆 Lv1，**材料湊得齊是數學保證，不是機率問題**。

期望值上每種屬性約 2.4 顆掉落，加上初始的 3 種各 1 顆，
多數屬性會在中段關卡前達到可融合門檻。

> ✅ **因此「融合能不能發生」不是待驗證項。**
> 真正待驗證的是「玩家願不願意融合」——即上方 −6.7% 下界的心理效果，
> 以及站位稀缺程度是否真如支柱②預期。兩者皆併入 Open Question #9。

## Edge Cases

### 嵌合操作

- **若嵌合時金錢不足 `C`**：操作被拒絕，UI 以灰化 + 抖動提示
  （沿用 art-bible §4 警示規則，不轉紅），不進入建造硬直。
- **若嵌合過程中巫師被擊殺**：操作中止，金錢不扣除，寶石留在庫存。
- **若嵌合過程中該塔被摧毀**：操作中止，金錢不扣除。
- **若準備期取下後未再嵌入即進入戰鬥**：該塔以基礎攻擊運作，無額外懲罰。

### 融合

- **若同屬性 Lv1 恰好 2 顆且全部已嵌在塔上**：需先取下才能融合。
  準備期取下免費，故無實質阻礙。
- **戰鬥期不可融合。** 融合僅限準備期與關卡外。
  理由：融合會消耗實例，若在戰鬥中執行可能突然讓多座塔失去寶石，造成防線瞬間崩潰。
- **若擁有 Lv1 超過 2 顆**：玩家自選要消耗哪 2 顆。

### 屬性剋制

- **剋制與被剋不可能同時成立**：相剋環上任兩屬性間至多一個方向，結構自帶互斥。
- **基礎塔（無屬性）攻擊任何敵人**：`AffinityMult` 恆為 1.0。
  不吃剋制加成，也不受被剋懲罰。
- **無屬性敵人**（`BaseAttribute = null` 且無賦予）：任何攻擊皆 ×1.0。
- **賦予屬性與天生屬性相同**：僅刷新時效，不疊加、不產生額外效果。
- **賦予屬性的時效在領域結束前歸零**：立即回歸 `BaseAttribute`，
  後續攻擊改以天生屬性判定。連攜的後段階段若晚於時效，就吃不到剋制——
  **這是連攜技設計時必須自我保證的約束**：後段階段的起始時間須早於前段賦予的時效終點。
- **同一敵人被兩個連攜領域先後賦予不同屬性**：後者覆寫前者，時效重新計算。

> ⚠️ **敵人屬性 × 屬性禁用挑戰的死局**
>
> 關卡的敵人屬性組合與該關挑戰目標的禁用項，**必須至少留下兩種可行的屬性解**
> （基礎塔不計入，因其無法觸發剋制）。
>
> 📌 **相剋環使這條規則更容易驗證**：敵人只有一個屬性欄位，
> 「哪些屬性能剋它」由環直接查出，不需要逐關手寫弱點表。
> 但也更容易誤踩——整關敵人屬性若過度集中，可行解會自動收斂到環上的單一屬性。
>
> 此為**關卡設計的硬性驗證規則**，違反則產生不可達成的星星，
> 牴觸 game-concept §4.3「限制型目標永遠可達成」。
>
> 📌 **規則精確化（`/design-review` 修訂新增）**：上述「兩種可行屬性解」是對
> **關卡資料**的驗證，不保證玩家**當下庫存**擁有這兩種寶石——5 種寶石全靠隨機掉落，
> 玩家仍可能在擁有這兩種屬性之外的組合時卡在某關（尤其是 90 秒限時、無傷等
> 沒有「慢慢用基礎塔磨」空間的挑戰模板）。**修正後的規則**：
> 這兩種可行屬性解，其中至少一種必須是玩家在該關卡**「正常掉落進度下，理論上已可能擁有」**
> 的屬性（即：計入該關卡之前所有已掉落寶石的屬性池，此屬性至少有機會已被玩家取得）。
> 三星挑戰以外的**主線通關路徑**必須保留「不需要特定屬性、基礎塔即可通過」的選項，
> 星星可以卡屬性運氣，**主線過關不行**。
>
> 📌 **範疇澄清（`/design-review` 修訂新增）**：本規則管的是**星星**的可達成性，
> 不是主線過關——主線的保底已由上一句的「基礎塔即可通過」選項單獨保證，
> 與本規則無關。因此本規則刻意採**「理論上非零機率」**而非「多數玩家機率上大概率擁有」
> 作為門檻：星星本就允許卡屬性運氣（見上句），本規則要防的是更嚴重的情形——
> 某星星目標所需的屬性組合，在該關卡進度下**對所有玩家都不可能取得**（保證性的不可達成，
> 而非機率性的運氣不好）。維持「理論可能」門檻是刻意選擇，不視為需收緊的漏洞。

### 疊加與同屬性並存

| 屬性 | 規則 |
|---|---|
| **火** | 燃燒區可疊加，**上限 3 層**。超過部分不生效——**同時生效層數超過 3 時，保留「單層傷害最高」的 3 層**（而非先到先得），確保高等級火塔的投資不會被更早抵達的低等級燃燒區鎖住名額。**此取捨為持續重估，非建立時快照**：每次有新燃燒層作用於該敵人時重新排序，若新層的單層傷害高於當前生效 3 層中的最低者，則最低者**立即失效**（不等其持續時間結束），由新層遞補。被擠下的層若其來源仍在持續時間內，可在名額釋出時重新遞補 |
| **霜** | 減速**不疊加，取最高值**。一次性傷害則每次進入新的減速場皆觸發——**「新場域」逐來源獨立判定**：每座霜塔各自對每隻敵人維護獨立的「已觸發」旗標。敵人對塔 A 的場域只觸發一次，但即使仍站在重疊區域內，只要同時進入塔 B 的場域範圍，仍會對塔 B 再觸發一次。旗標於敵人完全離開該座塔的場域範圍後重置。此判定與是否重疊、路徑抖動無關，避免邊界抖動造成的重複觸發爭議 |
| **雷** | **可重複命中同一目標**，但總跳躍次數上限 4，且每跳 −20% |
| **風** | 擊退**不疊加**。同時命中時只套用一次，**取所有命中中隨機滾骰結果最大（距離最遠）的一次**——判定式明確，不依賴命中順序或系統的迭代次序，避免同局不同次執行結果不一致。**「同時」定義為同一次傷害結算批次（same damage-resolution pass）**：所有塔於該批次內產生的擊退請求先全部入列，批次結束時才統一裁決並套用一次位移。跨批次的擊退各自獨立生效，不受此規則約束 |
| **蝕** | 穿甲**可疊加**，但受 25% 下限約束 |

### 數值邊界

- **`BaseArmor = 0` 的敵人**：`EffectiveArmor = 0`。
  穿甲對無甲敵人無額外效果，蝕退化為普通單體攻擊。
- **`ArmorReduction` 上限 0.75**：即使防禦力極高，傷害減免不超過 75%，
  確保任何攻擊都能造成傷害（呼應「絕不做免疫」原則）。
- **雷在場上僅剩 1 隻敵人時**：所有跳躍集中於該敵人，總傷害仍受 336.2% 上限約束。
- **霜的減速場範圍內無敵人時**：持續維持，不消耗資源，無效果。

### 關卡週期

- **關卡結束（勝或敗）**：所有嵌合狀態清空，寶石全數回庫存，嵌入費不退還。
- **關卡失敗重試**：庫存與寶石等級不變，**無任何懲罰**
  （呼應 game-concept §7 心流設計的低重試成本）。

## Tuning Knobs

| 參數 | 建議起始值 | 過高會怎樣 | 過低會怎樣 |
|---|---|---|---|
| `C`（嵌入費） | 建造費的 **60%** | 玩家不敢嵌合，全場基礎塔 | 嵌合無成本感，基礎塔失去意義 |
| `WeaknessMult` | **1.5** | 不用對屬性等於不能玩 | 剋制失去意義 |
| `ResistMult` | **0.75** | 用錯屬性等同浪費，違反「輕鬆」 | 被剋感受不到 |
| `LevelMult(Lv2)` | **1.2** | 等級輾壓屬性選擇 | 升級沒有價值 |
| `FusionCost` | **2 顆**（`/design-review` 修訂由 3 調降） | MVP 內升不了任何一顆 | 升級太廉價，失去「數量 vs 品質」取捨 |
| `ArmorFloorRatio` | **0.25** | 穿甲效果太弱，蝕失去定位 | 重甲敵人失去質感 |
| `ArmorReductionCap` | **0.75** | 出現實質免疫，違反反支柱⑤ | 防禦力失去意義 |
| `ArmorReductionScale`（`K`） | **200**（待原型實測調整） | 穿甲/防禦力幾乎沒有存在感（減免太容易衝頂） | 防禦力幾乎不減傷，蝕的穿甲價值被稀釋 |
| `FireStackCap` | **3 層** | 堆滿火塔成為最優解 | 集火沒有價值 |
| `ChainJumps` | **4 次** | 雷過強，壓過其他屬性 | 鏈式特色不明顯 |
| `ChainFalloff` | **0.8** | 雷的總傷害發散 | 跳躍幾乎沒收益 |
| `KnockbackVariance` | **±40%** | 風塔感覺不可靠 | 隨機性感受不到，回到可精算的鎖位 |
| `GemDropPerLevel` | **2 顆** | 收集太快，稀缺感消失 | 湊不滿 5 種，連攜放不出來 |
| `InitialGemCount` | **3 顆**（3 種各 1，**種類非隨機，見下方硬性約束**） | 前期沒有解鎖感 | 前期連攜放不出來，MVP 驗證不了核心循環 |

> ⚠️ **互動警告**：`C` 與 `GemDropPerLevel` 互相牽制——
> 寶石多但嵌不起，或嵌得起但沒寶石，兩種失衡都會讓系統空轉。
> 調整任一項時須同時檢查另一項。

> 📌 **硬性約束——起始 3 顆寶石的種類須對齊連攜技**：
> `InitialGemCount` 的 3 種寶石**不可隨機選取**，必須涵蓋 MVP 3 個連攜技中
> **至少一個技能的完整配方**，確保玩家第一關就能組出至少一次連攜。
>
> ✅ **已回填（2026-09-20，來源：game-concept §3.2 MVP 三個連攜技定案）**
>
> **起始 3 顆 ＝ 火、霜、風（各 1 顆）。**
>
> | MVP 連攜技 | 配方 | 起始是否湊得出 |
> |---|---|---|
> | ① 霜 → 火「炎寒領域」 | 霜×1 ＋ 火×1 | ✅ |
> | ② 火 → 霜「凍土」 | 火×1 ＋ 霜×1 | ✅ |
> | ③ 火 → 風「星星之火」 | 火×1 ＋ 風×1 | ✅ |
>
> **三個技能第一關全部可用**，遠超過「至少一個」的最低要求。
> 連攜的實際解鎖由技能樹節點控制，不由寶石控制——玩家點開哪個就能立刻用。
>
> ⚠️ **雷與蝕在 MVP 無對應連攜技。** 3 個技能最多覆蓋 3–4 種屬性，
> 這是數學極限不是疏漏。兩者仍是可用的塔寶石（跳彈、穿甲），
> 且是 v1.0 擴充連攜技時的主要素材。

## Acceptance Criteria

> 📌 **數值容許誤差（`/design-review` 修訂新增）**：以下所有涉及浮點數比較的
> AC，數值比對容許誤差為 `±0.001`，避免因浮點捨入被誤判為失敗。

> 📌 **依賴標記**：標示 ⚠️ 的 AC 依賴尚無 GDD 的上游系統（塔／傷害計算／敵人／
> 建造／事件匯流排／連攜／三星挑戰）。測試計畫須以 stub／mock 實作這些依賴的
> 介面契約後才能執行，不可視為「等上游系統完成後才寫測試」。

### 核心規則

- ⚠️ **GIVEN** 一座已建造但未嵌合的塔，**WHEN** 敵人進入其射程，
  **THEN** 該塔以基礎攻擊（單體、索敵第一隻、基準攻速）攻擊，且 `AffinityMult = 1.0`。
- ⚠️ **GIVEN** 一座已嵌合火寶石的塔，**WHEN** 敵人進入射程，
  **THEN** 該塔停止基礎攻擊，改為週期性投放燃燒區。
- **GIVEN** 玩家擁有一顆已嵌合的寶石，**WHEN** 嘗試將其嵌入第二座塔，
  **THEN** 操作被拒絕。
- **GIVEN** 玩家金錢少於 `C`，**WHEN** 嘗試嵌合，**THEN** 操作被拒絕。
- **GIVEN** 玩家金錢少於 `C`，**WHEN** 嘗試嵌合，**THEN** 不扣款。
- ⚠️ **GIVEN** 玩家金錢少於 `C`，**WHEN** 嘗試嵌合，**THEN** 不進入建造硬直（依賴建造系統介面）。
- **GIVEN** 玩家金錢少於 `C`，**WHEN** 嘗試嵌合，**THEN** UI 顯示灰化 + 抖動，不轉紅。
- **GIVEN** 嵌合操作進行中，**WHEN** 巫師於此期間被擊殺，
  **THEN** 操作中止、金錢不扣除、寶石留在庫存（不進入嵌合狀態）。
- **GIVEN** 嵌合操作進行中，**WHEN** 該塔於此期間被摧毀，
  **THEN** 操作中止、金錢不扣除。

### 經濟模型

- **GIVEN** 準備期已嵌合一顆寶石（已扣 `C`），**WHEN** 玩家取下該寶石，
  **THEN** 金錢回復至嵌合前的數額。
- **GIVEN** 戰鬥期已嵌合一顆寶石，**WHEN** 玩家取下該寶石，
  **THEN** 金錢**不**回復，寶石退回庫存。
- **GIVEN** 一座已嵌合的塔，**WHEN** 該塔被敵人摧毀，
  **THEN** 寶石回到庫存，且 `C` 不退還。
- 📌 **GIVEN** 準備期已嵌合一顆寶石（已扣 `C`），**WHEN** 玩家將其替換為另一顆寶石，
  **THEN** 舊寶石全額退還 `C`、新寶石扣款 `C`，玩家淨支出為 0
  （`/design-review` 修訂新增——原版本「嵌合經濟模型」表已定義此案例，但缺少對應 AC）。
- 📌 **GIVEN** 戰鬥期已嵌合一顆寶石，**WHEN** 玩家將其替換為另一顆寶石，
  **THEN** 舊寶石的 `C` 不退還、新寶石另外扣款 `C`，玩家淨損失為兩份 `C`
  （`/design-review` 修訂新增，同上）。

### 公式

- **GIVEN** Lv1 火寶石塔攻擊一隻弱火、無甲的敵人，**WHEN** 命中，
  **THEN** 傷害為 `BaseDamage × 1.5`（誤差 ±0.001）。
- **GIVEN** Lv2 火寶石塔攻擊一隻抗火、無甲的敵人，**WHEN** 命中，
  **THEN** 傷害為 `BaseDamage × 0.9`（誤差 ±0.001）。
- ⚠️ **GIVEN** 一隻 `BaseArmor = 100` 的敵人身上有總計 90 點穿甲，
  **WHEN** 計算有效防禦力，**THEN** 結果為 `25`（下限生效），而非 `10`（依賴敵人系統 `Armor` 欄位）。
- **GIVEN** 一座雷塔對兩隻敵人施放且全部跳躍命中，**WHEN** 結算總傷害，
  **THEN** 總和為 `BaseDamage × 3.362`（誤差 ±0.001）。
- **GIVEN** 一隻敵人同時位於 5 個燃燒區內（層級不一），**WHEN** 結算燃燒傷害，
  **THEN** 僅「單層傷害最高」的 3 層生效，其餘 2 層不計入。
- **GIVEN** 一隻敵人身上已有 3 層生效中的燃燒（單層傷害 10 / 10 / 8，皆未到期），
  **WHEN** 一座 Lv2 火塔於此時投放單層傷害 12 的新燃燒區並覆蓋該敵人，
  **THEN** 傷害 8 的那層**立即失效**（不等其持續時間結束），生效組合變為 12 / 10 / 10；
  **WHEN** 其中一層傷害 10 的燃燒區到期，**THEN** 若傷害 8 的來源仍在持續時間內，
  該層重新遞補為生效（驗證「持續重估」而非「建立時快照」）。
- **GIVEN** 一隻敵人同時被 3 座風塔命中（同一次傷害結算批次），**WHEN** 結算擊退，
  **THEN** 僅套用其中「隨機滾骰距離最大」的一次擊退，其餘 2 次不生效。
- **GIVEN** 一隻敵人先後於**兩個不同的傷害結算批次**各被一座風塔命中，**WHEN** 結算擊退，
  **THEN** 兩次擊退各自獨立生效（驗證不疊加規則的範疇僅限單一批次內）。
- ⚠️ **GIVEN** 一隻敵人身上疊加 4 次蝕的穿甲 debuff（每次 30 點），**WHEN** 計算有效防禦力，
  **THEN** `ΣPenetration = 120` 全數計入疊加公式，但最終結果仍受 25% 下限約束
  （依賴敵人系統 `Armor` 欄位）。

### 融合

- **GIVEN** 玩家擁有 2 顆同屬性 Lv1 寶石，**WHEN** 於準備期執行融合，
  **THEN** 該 2 顆自庫存移除，新增 1 顆同屬性 Lv2。
- **GIVEN** 戰鬥期進行中，**WHEN** 玩家嘗試融合，**THEN** 操作被拒絕。
- **GIVEN** 玩家擁有的同屬性 Lv1 恰好 2 顆且全部已嵌在塔上（準備期），**WHEN** 玩家嘗試融合，
  **THEN** 操作被拒絕並提示「須先取下」；**WHEN** 玩家接著取下全部 2 顆，
  **THEN** 金錢全額退還且融合操作變為可執行。
- **GIVEN** 於關卡外（非準備期、非戰鬥期）擁有 2 顆同屬性 Lv1 寶石，**WHEN** 執行融合，
  **THEN** 操作成功（驗證「融合僅限準備期與關卡外」規則的另一半——關卡外亦可執行）。

### 跨系統

- ⚠️ **GIVEN** 場上有一座火塔與一座霜塔，**WHEN** 連攜系統查詢塔屬性，
  **THEN** 正確回傳「火」與「霜」（依賴連攜系統 `GetTowerAttribute` 介面契約）。
- **GIVEN** 玩家嵌合一顆寶石，**WHEN** 操作完成，
  **THEN** 事件匯流排廣播 `OnGemSocketed`（本系統責任範圍到此為止；
  三星挑戰系統是否正確訂閱並更新「本關已使用屬性集合」屬於三星挑戰系統自身的 AC）。
- **GIVEN** 關卡失敗並重試，**WHEN** 進入新一局，
  **THEN** 玩家的寶石庫存與等級與失敗前完全相同。
- **GIVEN** 一場關卡成功結算（過關），**WHEN** 結算完成，
  **THEN** 所有嵌合狀態清空、寶石全數回庫存、嵌入費 `C` 不退還
  （驗證「關卡週期」Edge Case 的成功分支，先前僅有失敗/重試分支有對應 AC）。

### 屬性賦予（`AppliedAttribute`）

- **GIVEN** 一隻 `BaseAttribute = null` 的敵人，**WHEN** 連攜對其 `ApplyAttribute(Frost, 2.0)`，
  **THEN** `AppliedAttribute == Frost` 且 `AppliedAttributeRemaining == 2.0`（±0.001）；
  **WHEN** 火屬性塔攻擊它，**THEN** `AffinityMult == 1.5`。
- **GIVEN** 該敵人的 `AppliedAttributeRemaining` 倒數至 0，**WHEN** 火屬性塔再次攻擊，
  **THEN** `AppliedAttribute == null` 且 `AffinityMult == 1.0`（回歸 `BaseAttribute = null`）。
- **GIVEN** 一隻 `BaseAttribute = Frost` 的敵人且當前無賦予，
  **WHEN** 對其 `ApplyAttribute(Frost, 2.0)`，
  **THEN** 判定結果不變（火打它仍為 1.5），且**不產生任何額外效果**，僅時效刷新為 2.0。
- **GIVEN** 一隻 `BaseAttribute = Fire` 的敵人，**WHEN** 對其 `ApplyAttribute(Frost, 2.0)`，
  **THEN** 在時效內 `Frost` **完全覆寫** `Fire`——火屬性塔打它為 ×1.5（而非天生的中立），
  蝕屬性塔打它為 ×1.0（而非天生的 ×1.5）；**WHEN** 時效結束，**THEN** 兩者回復為天生判定。
- **GIVEN** 一隻已被賦予 `Frost`（剩餘 1.0 秒）的敵人，**WHEN** 另一個領域對其
  `ApplyAttribute(Wind, 2.0)`，**THEN** `AppliedAttribute == Wind` 且
  `AppliedAttributeRemaining == 2.0`（後者覆寫前者，時效重新計算而非累加）。
- **GIVEN** 任意敵人，**WHEN** 以 `null` 呼叫 `Counters()`，**THEN** 回傳 `false`
  （無屬性方永不參與剋制判定）。
- **GIVEN** 攻擊屬性與敵人屬性相同（如火打火），**WHEN** 查詢相剋環，
  **THEN** `AffinityMult == 1.0`（同屬性為中立，環上無自剋關係）。

### 關卡資料驗證

|---|---|---|
| `levelEnemyAttributes` | `Set<GemAttribute>` — 該關所有敵人 `BaseAttribute` 的非 null 集合 | 關卡與章節進程 |
| `bannedAttributes` | `Set<GemAttribute>` — 該關三星挑戰禁用的屬性 | 三星挑戰 |
| `cumulativeDropPool` | `Set<GemAttribute>` — 玩家打到該關時，**理論上可能已擁有**的屬性集合。定義為「初始 3 種 ∪ 前置所有關卡掉落表的種類聯集」 | 關卡與章節進程 |

**可行屬性解**的定義：屬性 `a` 為可行解 ⟺
`a ∉ bannedAttributes` 且 `∃ e ∈ levelEnemyAttributes, Counters(a, e) == true`。
（基礎塔不計入——無屬性無法觸發剋制。）

- **GIVEN** `levelEnemyAttributes = {Frost, Lightning}`、`bannedAttributes = {}`、
  `cumulativeDropPool = {Fire, Frost, Lightning}`，**WHEN** 執行驗證，
  **THEN** 通過——可行解為 `{Fire, Frost}`（火剋霜、霜剋雷），共 2 種，
  且 `Fire ∈ cumulativeDropPool`。
- **GIVEN** `levelEnemyAttributes = {Frost}`、`bannedAttributes = {Fire}`，
  **WHEN** 執行驗證，**THEN** **失敗**——唯一能剋霜的是火，已被禁用，可行解數量為 0。
- **GIVEN** 可行解為 `{Wind, Eclipse}` 但 `cumulativeDropPool = {Fire, Frost, Lightning}`，
  **WHEN** 執行驗證，**THEN** **失敗**——可行解數量達標（2 種），
  但**無一在玩家理論上可持有的集合內**。
- **GIVEN** 任一驗證失敗的關卡資料，**WHEN** 嘗試將該關標記為可發布，
  **THEN** 操作被阻擋，並回報失敗原因（可行解不足 / 可行解不在掉落池內）。

> ⚠️ **本驗證函式的宿主是關卡與章節進程系統，不是本系統。**
> 本節定義的是**契約與斷言**；「關卡設計師如何確保通過」（掉落順序安排、
> 挑戰模板的出現時機）屬於該系統的職責，本 GDD 不越界規範。
> 已登記於 systems-index §8。
