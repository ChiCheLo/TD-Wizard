## Overview

**這個系統是什麼**（資料層）：連攜系統是巫師技能與塔防禦網之間的**配方比對與效果生成引擎**。它定義每個連攜技能的配方（所需屬性×固定數量）、階段順序、生效範圍（落點圓）與效果內容，並在巫師施放時檢查範圍內符合配方的塔，推進技能的階段時間軸，最終在準心指定的區域或目標上生成效果。

**玩家怎麼碰到它**（設計層）：玩家透過站位把自己變成配方的「檢查點」——走到能同時涵蓋所需屬性塔的位置，按下技能鍵進入施法模式，瞄準落點後確認施放。玩家不直接操作連攜的效果本身，只操作**觸發的時機與位置**；效果一旦觸發便自動依階段推進。

**為什麼這個系統存在**：沒有連攜系統，場上的塔只是各自獨立開火的砲台——寶石決定了塔打什麼，但決定不了「塔之間如何互相成就」。連攜系統是唯一能把獨立的塔連成戰術網路的機制，也是核心幻想「我是網路的節點」唯一的實現路徑。若拿掉連攜系統，遊戲會退化成普通塔防，支柱②「站位就是資源」會完全失去意義。

## Player Fantasy

**核心幻想**：「我是這張網路的節點。」

玩家不是戰場上最強的戰士——巫師的基礎輸出刻意壓低（見待解問題#1，交由巫師能力 GDD 定案下限）。玩家的價值感完全來自**讓場上各自為政的塔產生關係**：兩座塔平時互不相干，是玩家走到正確的位置、在正確的時機按下技能鍵，它們才因為玩家的存在而連動起來。

這個幻想在連攜系統裡具體落實為三個瞬間：
1. **站位判讀**——掃視戰場，找出哪些塔的屬性組合能湊出配方，決定要往哪走
2. **時機賭注**——0.3 秒前搖霸體前可被打斷，意味著「現在放」是有風險的主動選擇，不是安全操作
3. **落點裁決**——按下技能鍵確認要放的瞬間，落點圓的圓心由巫師與參與塔的相對位置決定並鎖定。站位不是連續跟隨的即時預覽，而是在關鍵瞬間被讀出的裁決：玩家必須在走位當下、在按鍵之前就對「這裡放得到」有把握，而不是邊看著圓邊微調位置。**這一版明確修正**：早期敘述曾暗示「巫師往前走、圓就即時跟著移動」——但落點圓實際上只在進入施法模式後才出現且立即鎖定快照，玩家不會在按鍵前看到圓的即時跟隨。「hover 預覽」（滑鼠移到技能列上就能預先看到落點圓）是這個落差的候選緩解方案，見文末待解問題#3。

> 注：Lean 模式下，Section B 不屬於高風險章節（D/H）。本機已可存取 `creative-director`／`game-designer` 等 agent；本輪 `/design-review`（full 模式）已由 `creative-director` 對本節的幻想交付進行了一輪覆核，發現「落點裁決」措辭與實際機制不符（已於上方修正）。`game-designer` 未包含在本次審查的可用 agent 清單中，本節尚未經過專屬 game-design 視角的深度覆核，正式製作前建議另尋機會補齊。

呼應支柱②「站位就是資源」：站位不是移動到安全區這種被動選擇，而是持續被爭奪的**主動資源**——中轉連攜、補強塔的維修、建造新塔都在搶同一個身體。呼應支柱①「配置勝於操作」：連攜的「威力」在站上去之前就由寶石配置決定了，玩家在戰鬥中做的是**時機與位置的判斷**，不是操作精度的展現（多數連攜技無瞄準、無連招輸入，符合反支柱③；**星星之火是本作唯一正式擴大反支柱③豁免範圍的技能，同時豁免區域式目標選取與精準對位操作前提**，見 Visual/Audio Requirements 的「瞄準鏡例外聲明」與 game-concept §3.2 的對應修訂）。

**參考基準**：不同於《Orcs Must Die!》系列裡玩家是主要輸出來源，這裡的爽感反轉了——你打得不多，但沒有你，那些塔就只是各自為政的砲台。連攜命中的瞬間，那種「這是我造成的」的歸屬感，才是這個系統要交付的情緒。

## Detailed Design

> 注：本節屬於高風險章節（D）。本輪 `/design-review`（full 模式）已由 `systems-designer` 對本節進行對抗式覆核，發現多項阻擋性問題（狀態機無法保證退出、CD 模型與「各技能獨立」的不變式衝突、感應半徑為不可學習的全域值等），皆已於本次修訂處理，詳見下方各節與文末 Open Questions。

### Core Rules

1. **技能綁定**：每個已解鎖的連攜技綁定一個固定快捷鍵（由天賦／技能樹系統決定解鎖與鍵位，連攜系統只接收「哪個 `skillId` 被按下」）。
2. **輸入互斥與搶佔**：技能鍵可隨時搶佔**施法模式（Aiming）**——若巫師正處於某技能的施法模式，按下另一個技能鍵，會立即取消目前的施法模式（無代價，同規則7）並切換進入新技能的施法模式，**條件是**：該技能已解鎖 ∧ 不在 `Cooldown` 中 ∧ 配方滿足，三者同時成立才會搶佔；不滿足任一條件時，此次按鍵輸入在 `Aiming` 期間完全被忽略，**不影響**目前正在進行的施法模式。玩家按下**目前正在 `Aiming` 的同一個技能**的鍵時，視為 no-op（不重取快照、不重新計算落點圓）。一旦進入**前搖（Windup）**或**短僵直（ShortStun）**，技能鍵輸入一律忽略，直到當前流程結束（取消、完成、或被打斷進入短僵直後）——前搖之後已是「確認要放」的階段，不該再被打斷選招。**本輪修訂**：`Active` 不再列入此鎖定清單——見規則8／規則10 的效果實例分離，`Active` 現為單幀轉場，全域機器同幀即回到 `Idle`，其餘技能鍵不再因此被鎖。
   > ⚠️ **同一幀內兩個技能鍵幾乎同時被偵測到**（真正意義上的同時輸入，非先後）：採固定優先序——依技能於技能列上的顯示順序（由天賦／技能樹的解鎖順序決定）取序位較前者生效，另一鍵輸入捨棄。不依賴引擎輪詢順序等不確定的實作細節。技能列的排序依據目前未定（見待解問題#5），測試須以注入固定順序的方式驗證此規則，不可等排序定案才寫測試。
   > ⚠️ **搶佔與取消的同幀優先序**（第2輪修訂新增，修正阻擋性洞）：若同一幀內，玩家按下技能鍵（可能觸發規則2搶佔）**且**規則7的取消條件（移動／受擊）同時成立，**取消恆優先**——該幀一律先判定取消（回到 `Idle`，不進 CD），該幀所有技能鍵輸入一律捨棄（不視為「取消後在 Idle 重新按鍵」）。與規則8「受擊優先於前搖完成」同一個保守方向：懲罰方向對玩家可預期。
   > ⚠️ **移動中按鍵**（第2輪修訂新增）：核心動作是巡邏，玩家經常處於移動狀態。若按下技能鍵的那一幀，移動軸輸入已超過死區，此次按鍵**直接視為無效**（不進入 `Aiming`，無回饋以外的副作用）——不是「先進入 Aiming 再被規則7取消」，兩者在資料上等價（都不觸發任何連攜事件），但語意上更單純：玩家必須先放開搖桿／WASD 至死區內，按鍵當幀才可能進入 `Aiming`。
3. **配方檢查**：按下技能鍵時，以巫師目前座標為圓心、`ChainDetectionRadius`（**固定常數旋鈕**，見 Tuning Knobs，provisional 值 6 公尺，待 `/prototype --spike` 驗證）為半徑，蒐集範圍內**已嵌合**的塔，依屬性分組。
   > ⚠️ **感應半徑必須有遲滯（第3輪修訂新增，阻擋性，`art-director` 覆核發現）**：`ChainDetectionRadius` 是一個 0/1 硬邊界，而巡邏是核心動作——玩家會整局黏在邊界附近微調位置（他們正是在找配方成立的站位）。無遲滯時可放性旗標會逐幀翻轉，技能列變成高頻閃爍的噪音。**這是資料層職責，不可下推給 UI**：UI 收到的是 bool，沒有能力知道自己在邊界上，art-bible §7 的「轉場 ≤0.1 秒淡入淡出」只會把逐幀翻轉變成呼吸燈，是症狀治療。
   > **規則**：某座塔**進入**感應範圍的判定距離為 `ChainDetectionRadius`（6.0 公尺）；**離開**的判定距離為 `ChainDetectionRadius + ChainDetectionRadiusHysteresis`（6.4 公尺，見 Tuning Knobs）。已納入的塔必須超出外圈距離才會被移除，尚未納入的塔必須進入內圈距離才會被納入。兩個距離皆採 XZ 水平距離、皆含邊界。`ChainDetectionRadius` 與塔的射程無關、不隨場上塔配置變動——感應範圍對玩家而言是一個可以直接記住的固定數字，不受地圖上其他塔影響（**本輪修訂**：原版本取「全場已嵌合塔攻擊半徑的最大值」，會讓地圖另一端一座塔悄悄改變巫師任何位置的感應範圍，規則不可學習、也無法做空間查詢優化；改為固定常數後兩個問題都不存在）。若任一分組數量 < 配方需求，此次按鍵無效（不進入施法模式，無回饋以外的副作用）。**場上無任何已嵌合塔時，分組結果必為空，配方必不滿足，此為正常情況，非例外或錯誤狀態。**
4. **參與塔篩選（超額情況）**：若某屬性符合的塔數量超過配方需求，取**距巫師最近的 N 座**（N＝配方需求數）作為參與塔；**距離相等時以塔的唯一實例 ID 升序排序決定**，確保結果可重現、非隨機。**MVP 因寶石為實例制，玩家可同時擁有多顆同屬性寶石，此規則在 MVP 即會生效**（原版本誤述為「MVP 暫不生效」，已修正——只要玩家帶了兩顆以上同屬性寶石並各自嵌合，篩選就會發生）；v1.0 配方可能要求同屬性 ×2 以上時，**資料結構須支援**篩出 N＞1 座。「靠近的塔優先」讓玩家能透過站位主動排除較遠、通常位置也較差的塔，把哪些塔算進配方交給站位決定，呼應支柱②——**但須注意**：落點圓半徑取的是參與塔中射程最大者，篩選較近的塔不必然縮小圓半徑，兩者是各自獨立的效果，不應混為一談。
5. **施法模式**：配方滿足後立即鎖定巫師移動（連攜系統對外暴露 `IsInCastMode()`，巫師能力系統讀取此狀態並自行忽略移動輸入——連攜系統不直接操作巫師的 Transform，維持 systems-index §3③ 的單向依賴）。目標選取透過**畫面中心準星 + 自動吸附**完成（沿用 game-concept §3.2 的操作前提，**不使用自由滑鼠游標**——**本輪修訂**：原版本誤寫為「滑鼠游標位置」，與 game-concept 的硬性約束「無自由游標，一律準星＋自動吸附」直接矛盾，已修正）：以巫師攝影機為原點、準心方向為射線，取與地面（或該技能宣告的目標平面）的交點作為候選落點；受 `CastCircle` 約束的技能將候選點限制於圓內，超出範圍時貼齊圓周邊緣（沿圓心→候選點方向取交點），而非拒絕輸入。**進入 `Aiming` 的當下，落點立即初始化為 `CastCircle` 圓心**（而非等待準心移動後才有值），確保按鍵當下就已經是一個合理解，呼應 game-concept §3.2 的硬性約束（施法模式停留時間 ≤1 秒）；之後準心的移動即時更新候選落點。
6. **確認**：玩家滑鼠左鍵按下即確認落點並進入前搖。**不使用停留預算自動確認**——`CastModeDwellBudget`（≤1.0 秒）定義的是「玩家最長合理反應時間」的設計上限驗證基準，不是自動觸發的計時器。
7. **取消（無代價）**：施法模式期間，符合下列任一情況 → 立即取消，回到 Idle，不進 CD、不消耗任何資源：
   - **移動輸入**：移動軸輸入超過巫師能力系統定義的搖桿死區閾值（沿用該系統既有的移動死區設定，本系統不另訂）；純視角旋轉（滑鼠移動／搖桿右搖桿）不算移動輸入。
   - **受到攻擊**：巫師承受一次**離散、傷害 > 0** 的敵方攻擊事件。**持續傷害（DoT／領域 tick）與傷害為 0 的效果（純擊退、純 debuff）不算「受到攻擊」**——本輪修訂新增，避免巫師站在灼燒或減速場中導致連攜永久無法施放。
   - **配方不再滿足**（第3輪修訂新增，阻擋性，`systems-designer` 覆核發現）：`Aiming` 期間**每幀重跑規則3的配方檢查**；任一參與塔被拆除、實體消失、寶石被取下，或因故不再持有配方所需屬性，導致配方不再滿足時 → 立即取消。廣播 `OnChainInterrupted(MaterialInvalidated)`（與前搖完成重驗失敗共用同一原因標記，見 Edge Cases）。
     > **為什麼需要這條**：原版本的 `Aiming` **沒有任何成本**——不會移動、不會因時間流逝而失效，AC30 還明文保證 t=10.0 秒仍維持 `Aiming`。於是最優解變成「進 `Aiming` 慢慢看、等安全了再點左鍵」，把 Player Fantasy 第二個瞬間「時機賭注」（現在放是有風險的主動選擇）完全繞過——風險被玩家挪到自己選定的安全時刻。加上配方持續重驗後，`Aiming` 不再是免費的暫停鍵：戰場持續變化，久駐本身就承擔材料被打掉的風險。**這是刻意選擇「讓戰場替代計時器」，而非引入 dwell 計時器**（規則6「不使用停留預算自動確認」維持不變，`CastModeDwellBudget` 仍是設計驗證基準而非計時器）。
     > 注意巫師移動**不會**改變參與塔集合——參與塔於進入 `Aiming` 當下即鎖定快照（規則5／Edge Cases），重驗只確認「快照中的這幾座塔是否仍然有效」，不重新篩選、不重算落點圓。
   取消判定於該幀輸入處理階段執行，**早於**巫師的移動積分；`IsInCastMode()` 於同一幀內轉為 false，確保巫師不會在取消生效前的那一幀被移動。
8. **前搖與判定**：確認後進入 0.3 秒前搖（`CastWindup`）。此期間受擊（定義同規則7）→ 進入短僵直（`ShortStunDuration`，見 Tuning Knobs），技能**不進 CD**，僵直結束後回到 Idle。前搖累計時間 ≥ `CastWindup`（0.3 秒）且未被打斷 → 進入 `Active`：同一幀內依序發生① 生成技能效果的**獨立效果實例**（見規則10）② 該效果實例的 Phase 1 立即生成、廣播 `OnChainConfirmed`／`OnChainPhaseAdvanced(1)` ③ **該技能的 CD 從此刻開始倒數 `ChainSkillCooldown` 秒**（而非按下技能鍵當下——因為前搖被打斷不進CD，CD 起點必須是「確定會生效」的那一刻）④ 全域施法狀態機**同幀**回到 `Idle`、`IsInCastMode()` 同幀轉為 `false`、巫師恢復移動、其餘技能鍵同幀恢復可用（除非各自在 CD 中）。**第2輪修訂**：`Active` 不再是一個會持續數秒的霸體狀態——它是「確認生效」與「效果實例誕生」之間的單幀轉場，效果本身的後續階段推進交給規則10的獨立效果實例追蹤，不佔用全域狀態機、不鎖定其他技能鍵、不鎖定巫師移動（原版本讓 `Active` 持續到效果最後階段結束，導致巫師整段效果期間霸體＋鎖鍵，違反 game-concept「放完即自由，不需站著維持」，見下方 States and Transitions 的說明）。**同一幀內若受擊判定與前搖完成判定同時成立，先處理受擊**（進入 `ShortStun`），確保懲罰方向對玩家保守、結果可預期（本輪修訂新增，原版本未定義此同幀衝突）。**CD 為每個技能各自獨立的計時器**，與目前是否有其他技能的效果實例正在推進無關——實作上不可用單一全域狀態表示 CD，見下方 States and Transitions 的三層模型。
9. **落點約束的逐技能宣告**：技能是否受 `CastCircle` 約束、目標選取方式（地面區域／單體／其他）、階段推進條件（計時自動／條件觸發／快照判定）皆由該技能自己的**策略定義**宣告，不寫死在核心流程的 switch/enum 裡（見 game-concept §3.2 硬性約束）。核心流程（規則1–8）對所有技能一致；技能差異全部封裝在各自的策略定義中。
10. **每個效果實例必須有保證的退出路徑**（第2輪修訂：從「`Active` 全域狀態的退出路徑」改為「效果實例自身的退出路徑」，語意更正確——見規則8）：每個技能的策略定義**必須**宣告一個有限的 `MaxActiveDuration`（例如「星星之火」= `EmberDuration` + 一段短暫的引爆判定窗，見 Formulas／Tuning Knobs 的預設值）。效果實例是一個獨立於全域施法狀態機的物件，自規則8生成的那一幀起自行倒數；無論各階段是否依技能自身條件正常推進完畢，效果實例在經過 `MaxActiveDuration` 後**強制**結束（尚未觸發的階段視為不生效，不補放，廣播 `OnChainCompleted`）。這保證任何技能的效果都不會無限期卡在推進中。**同一技能的 CD（規則8，於效果實例誕生當幀即開始倒數）恆長於其自身 `MaxActiveDuration`**（見 Formulas 不變式），因此同一技能不會有兩個效果實例同時存在；**不同技能的效果實例允許同時並行**（例如「炎寒領域」的領域仍在燒，玩家同時放出「星星之火」）——巫師是機動節點、需要能連續巡邏並視情況觸發不同連攜，效果實例彼此獨立運作不互相鎖定或搶佔。
11. **巫師陣亡**（本輪修訂新增，原版本無此規則）：巫師在 `Aiming`／`Windup`／`ShortStun` 期間死亡 → 立即返回 `Idle`（或依遊戲流程系統轉入死亡/結算狀態，由該系統決定）；`Aiming`／`Windup` 中的技能視為取消，不進 CD；已生成的效果實例（領域、標記）**維持既有規則繼續作用**直到自然結束或 `MaxActiveDuration` 到期（與 Edge Cases「敵人在階段作用期間死亡」的處理精神一致——效果作用於區域/目標，不依賴施放者存在），但不會再推進尚未觸發的後續階段；已進 CD 的技能維持倒數不受影響。**第2輪修訂**：因 `Active` 已改為單幀轉場（規則8），巫師死亡時全域機器幾乎不可能停留在 `Active`，此規則實務上只需處理 `Aiming`／`Windup`／`ShortStun` 三態；效果實例的存續不受巫師死亡影響這件事，維持不變。
12. **星星之火的目標鎖定時機**（第2輪修訂新增，修正阻擋性洞）：左鍵確認（規則6）的**同一幀**，以當下的準心 raycast 結果鎖定目標敵人實例 ID（含「未命中任何 hit box」的空結果）作為快照；前搖（Windup）期間玩家可自由旋轉視角（規則7允許），但**不會改變已鎖定的目標**——前搖完成後，Phase 1 的點燃判定只認快照中的目標 ID，不重新 raycast。若快照目標在前搖期間死亡或被物件池回收，視同快照為「未命中」處理（不產生火種標記，見 Edge Cases）。這確保「打空一樣進 CD，沒有免費重試」（Edge Cases）在任何實作路徑下都成立。
13. **`ShortStun` 不可重入**（第2輪修訂新增，修正阻擋性洞）：`ShortStun` 期間巫師若再次受到攻擊，該次受擊事件**一律忽略**——不延長、不重置 `ShortStunDuration` 倒數計時。僵直計時器自進入 `ShortStun` 的那一刻起單調倒數至 0，不受後續受擊影響。避免怪群密集（連攜最需要被放出來的場景）時巫師被連續命中而永久卡在僵直。

> 📌 **`IsInCastMode()` 真值表**（第2輪修訂新增，修正阻擋性洞——原版本只定義了 `Aiming`，其餘狀態下巫師能力系統無從得知是否該鎖移動）：

| 全域狀態 | `IsInCastMode()` | 移動是否鎖定 | 視角旋轉是否允許 |
|---|---|---|---|
| Idle | `false` | 否 | 是 |
| Aiming | `true` | 是 | 是 |
| Windup | `true` | 是 | 是（規則12：旋轉不改變星星之火已鎖定的目標） |
| ShortStun | `true` | 是（僵直中談不上主動移動） | 是 |

> `Active` 不在此表中——見規則8，它是單幀轉場，同一幀內完成生成效果實例並回到 `Idle`，`IsInCastMode()` 在該幀結束時已是 `false`。

### States and Transitions

> **本輪修訂**：原版本把 `Cooldown` 放進同一張狀態表，但 `Aiming` 可在技能間切換證明這是一個**全域**狀態機——而 `Cooldown` 卻被描述成「該技能專屬」，兩者矛盾，照表面實作會讓放技能①鎖住技能②③整整 30 秒，違反「各技能獨立 CD」的不變式。改為兩層模型：**一個全域施法狀態機**（整個系統同時只有一份）＋ **每個技能各自獨立的可用性計時器**。
>
> **第2輪修訂（阻擋性）**：上述兩層模型解決了 CD 層面的耦合，但把「巫師的施法狀態」與「技能效果的生命週期」都塞進同一個 `Active`，造成兩層模型沒解決的同一類問題以另一種形式復發——`Active` 依技能自訂階段清單推進、霸體、鎖定所有技能鍵，對星星之火而言持續 `MaxActiveDuration`（8 秒以上）。這違反 game-concept 的硬性不變式「巫師一次性施放 — 放完即自由，不需站著維持」，且讓「放技能①鎖住技能②③」的問題只是從 30 秒縮短為 8 秒，並未消失。修法：改為**三層模型**——① 全域施法狀態機（只負責 Idle/Aiming/Windup/ShortStun，`Active` 收斂為單幀轉場）② 每技能可用性計時器（不變）③ **新增：效果實例（Effect Instance）**——技能效果的階段推進與 `MaxActiveDuration` 倒數，交給一個獨立於全域狀態機的物件追蹤，不鎖定巫師移動、不鎖定其他技能鍵。

#### ① 全域施法狀態機

| 狀態 | 說明 | 可轉移至 |
|---|---|---|
| **Idle** | 待命，持續檢查所有已解鎖技能的配方是否滿足（用於 UI 顯示「可放」提示） | Aiming（按鍵、該技能不在 Cooldown 中、且配方滿足；規則2 的移動死區與取消優先序條件亦須成立） |
| **Aiming**（施法模式） | 巫師鎖定移動，顯示落點預覽；**每幀重驗配方**（規則7，第3輪修訂） | Idle（移動／受擊／配方不再滿足 三者任一取消，規則7）、Aiming（另一技能鍵搶佔且該技能不在 Cooldown 中，規則2，切換為該技能的 Aiming）、Windup（左鍵確認） |
| **Windup**（前搖 0.3s） | 霸體前的可打斷窗口，鎖定所有技能鍵輸入（規則2） | ShortStun（受擊）、Idle（前搖完成；同幀①生成效果實例②該技能進 CD③全域機器回到 Idle，見規則8） |
| **ShortStun** | 短僵直（`ShortStunDuration`），技能未觸發，鎖定所有技能鍵輸入（規則2），**不可重入**（規則13） | Idle（僵直結束，不進CD） |

> **`Active` 不再是這張表的一個持續狀態**：規則8 中「進入 Active」的那一刻，在全域狀態機的觀點裡就是「Windup 完成 → 同幀生成效果實例、該技能進 CD → 同幀回到 Idle」這一整串同幀事件——沒有任何一幀全域機器會停留在會鎖鍵、鎖移動的 `Active`。事件匯流排仍會廣播 `OnChainConfirmed`／`OnChainPhaseAdvanced(1)` 標記「效果已生效」，供動畫／VFX 訂閱一次性的 Active-start Peak（見 Visual/Audio Requirements），但這是**效果實例的生命週期起點**，不是全域狀態機的常駐狀態。
> `Windup`、`ShortStun` 期間，其他技能鍵輸入一律忽略（規則2）；只有 `Aiming` 狀態能被其他技能鍵搶佔，且搶佔對象必須不在 Cooldown 中。

#### ② 每技能可用性（與全域狀態機並存，每個已解鎖技能各自一份）

| 狀態 | 說明 | 可轉移至 |
|---|---|---|
| **Ready** | 可被規則3的配方檢查選中 | CoolingDown（效果實例於規則8的同幀生成時立即轉移，與全域機器回到 Idle 同幀，見規則8） |
| **CoolingDown** | `ChainSkillCooldown` 倒數中；此技能鍵在全域機器的 `Idle`／`Aiming` 中皆視為「配方不滿足」處理，不可被按鍵觸發也不可搶佔他人 | Ready（CD 歸零） |

#### ③ 效果實例（每次成功施放各自產生一份，第2輪修訂新增）

| 狀態 | 說明 | 可轉移至 |
|---|---|---|
| **Spawned**（誕生） | 於規則8的同幀建立，Phase 1 立即生成 | 依技能策略定義推進至下一階段，或直接進 Completed（單階段技能） |
| **PhaseN**（第 N 階段） | 依技能策略定義的推進條件（計時自動／條件觸發／快照判定，規則9）等待下一階段 | 下一個 PhaseN+1；或 Completed（最後階段自然結束，**或**達到 `MaxActiveDuration` 強制結束，規則10） |
| **Completed** | 廣播 `OnChainCompleted`，效果實例銷毀 | — |

> 效果實例**不影響**全域施法狀態機（①）——它誕生的那一刻，全域機器已經同幀回到 `Idle`。它也**不影響**其他技能的可用性（②）——不同技能的效果實例可同時並行存在（規則10）。它只受自己的 `MaxActiveDuration` 約束。巫師可以在自己的「炎寒領域」效果實例仍在燒的同時，走位觸發「星星之火」——這正是「巫師是機動節點、持續巡邏」這個核心動作在連攜多技能並存下的直接體現。

**ChainSkillDamage**（巫師傷害貢獻公式，**第3輪修訂：單一係數拆分為 tick 型與爆發型兩個係數**）

`ChainSkillDamage = WizardBaseDamage × ChainDamageMult_<型別>`

| 變數 | 型別 | 範圍 | 說明 |
|---|---|---|---|
| `WizardBaseDamage` | float | 待定（巫師能力 GDD 定案的固定常數）；**開發期 stub = 20**（與 AC43 一致，第3輪新增）| MVP 為固定值，非成長軸（裝備系統列入v1.0後才成長）。⚠️ 未給 stub 時 C# 預設值為 0，會讓三招連攜靜默零傷害且無任何 AC 攔得住——故此處強制登記 stub |
| `ChainTickDamageMult` | float | 0.5（provisional）| **tick 型**：領域類技能的每次判定各自套用（「炎寒領域」火海階段、「凍土」熔岩灼燒） |
| `ChainBurstDamageMult` | float | 2.5（provisional，第3輪新增）| **爆發型**：單次判定即交付全部傷害的技能（「星星之火」引爆） |

> 📌 **為什麼必須拆分（第3輪修訂，阻擋性，`systems-designer` 發現、`creative-director` 判定為全場唯一致命問題）**：
> 原版本 `ChainDamageMult = 0.5` 明文「三技能通用」，同時又澄清該值是**每次判定**的基礎值。兩者相乘的後果從未被推導出來：
> ```
> 炎寒領域 火海：2 秒 ÷ 0.5 秒 tick = 4 次判定 × 0.5 = 2.0 × WizardBaseDamage
> 凍土　　 熔岩：同上                              = 2.0 × WizardBaseDamage
> 星星之火 引爆：單次判定        × 0.5           = 0.5 × WizardBaseDamage
> ```
> 三者**同樣 30 秒 CD、同樣 ×1+×1 配方成本**，星星之火卻只交付 25% 的傷害——而且它額外要求精準瞄準（本作唯一的反支柱③豁免）、可以完全打空且打空照樣進 CD（見 Edge Cases）、還需要一座風塔在對的位置於 8 秒內命中。**沒有任何一個軸上它是有競爭力的。**
> 這不是平衡微調問題，是**單位錯誤**：把「每次判定的係數」套用在一個只有一次判定的技能上。game-concept §3.2 明訂星星之火是「三個技能裡最貼核心動詞『接通』的一個」——它應該是 MVP 裡最有爽感的一招，不是最差的一招。
> `ChainBurstDamageMult` 的 provisional 起點 2.5 = tick 型的等效總量（2.0）＋ 0.5 的溢價，用以補償打空風險與瞄準要求。**此數值待 `/prototype --spike` 驗證**；但**拆分本身不是平衡決定，是單位正確性**，不隨原型結果回退。
> **使用者於第3輪修訂明確決定**：保留星星之火與其反支柱③豁免，以拆分係數的方式補上它應得的回饋，而非將其砍出 MVP。

> 📌 **單位澄清（本輪修訂新增，修正阻擋性歧義）**：`ChainSkillDamage` 是**餵給 gem-socketing `FinalDamage` 管線的 `BaseDamage` 輸入值**，代表**該效果單次判定**（一次 tick、一次命中，判定頻率由各技能策略定義宣告）造成的基礎傷害，**不是**每秒傷害、也不是整個階段的傷害總和。「炎寒領域」火海階段若以每 0.5 秒一次 tick 運作，2 秒內共 4 次判定，每次都各自套用 `ChainSkillDamage` 進入 `FinalDamage`。
> 📌 **每技能適用的係數（第3輪新增，策略定義必須宣告）**：每個技能的策略定義須宣告自己採用 `ChainTickDamageMult` 或 `ChainBurstDamageMult`，不由形態推導（比照規則9的逐技能宣告精神）。MVP 三技能：炎寒領域＝tick、凍土＝tick、星星之火＝burst。
> `LevelMult`（gem-socketing `FinalDamage` 的組成之一）對連攜傷害固定為 **1.0**——連攜傷害不隨參與塔的寶石等級成長，維持 MVP「巫師基本傷害為固定常數，不隨任何配置成長」的既定範圍（game-concept §10）。
> 完整管線：`FinalDamage = ChainSkillDamage × 1.0(LevelMult) × AffinityMult × (1 − ArmorReduction)`，`AffinityMult` 由 gem-socketing 的 `Counters()` 查詢決定（**術語更正**：舊稱 `WeaknessMult` 已由 gem-socketing 改版為 `AffinityMult`，下方範例已同步更新）。

**輸出範圍**：0.5 × `WizardBaseDamage`（單次判定基礎值，尚未疊加 `AffinityMult`、護甲減免）
**範例**：若 `WizardBaseDamage` 未來定為 20，「炎寒領域」火海階段每次判定基礎傷害 = 10；若該次判定命中持有霜屬性的敵人，套用 `AffinityMult = 1.5`（火剋霜）＝ 15，最後再經 `FinalDamage` 公式套用護甲減免。

## Edge Cases

> 注：本節於本輪 `/design-review`（full 模式）由 `systems-designer` 覆核，發現數項遺漏（巫師陣亡、與已核准文件疊加政策不一致、參與塔消失與「塔是材料」不變式衝突等），已於下方處理。

- **若參與領域效果的敵人在階段作用期間死亡**：領域效果對區域生效，不依賴特定敵人存在；其餘留在區域內的敵人不受影響，效果持續作用到該階段結束。
- **若敵人在階段1結束前離開領域範圍、之後又重新進入**：**本輪修訂**——比照 gem-socketing 霜減速場「逐來源獨立判定」的既有政策：每個領域實例各自對每隻敵人維護一個「已觸發」旗標；敵人完全離開該領域範圍後旗標重置，重新進入才視為新的一次接觸判定。這避免了邊界抖動造成的重複觸發爭議（與 gem-socketing 處理相同問題的理由一致）；除非該技能自己在策略定義中明確聲明不同的接觸判定規則，否則一律採此預設政策。（原版本採「不做去重複判定」，與 gem-socketing 已核准的處理方式相反且無理由，已修正。）
- **「炎寒領域」暴風雪賦予的霜屬性時效訂為 `AppliedAttributeDuration_炎寒領域 = 4.5` 秒**（階段1剩餘最長2秒 + 階段2全長2秒 + 0.5秒安全邊際）：若敵人在階段1一開始就進入領域，時效足以覆蓋到階段2結束且不卡在臨界。**本輪修訂**：原版本為 4.0 秒——但敵人在階段2最後一次判定的時間點恰好等於時效終點，依 gem-socketing AC「倒數至0即回歸 `BaseAttribute`」，該次判定會**剛好吃不到剋制**，4.0 秒本身就是臨界失敗值。加上 0.5 秒邊際後不再卡臨界。
  > 📌 **邊界語意（第3輪修訂，修正自相矛盾）**：時效判定為**左閉右開**——`t < 4.5` 有效、`t = 4.5` 已過期，與 gem-socketing「倒數至0即回歸 `BaseAttribute`」一致。原 AC44 斷言「恰好第 4.5 秒（含邊界）仍視為有效」與上述「4.0 是臨界失敗值」的推導直接相反：若終點含入，4.0 從來就不是失敗值，整個 4.0→4.5 的調整理由會一併崩塌。**4.5 秒的正當性來自 0.5 秒安全邊際讓最後一次判定（≤4.0 秒）遠離邊界，不是來自邊界含入**（`systems-designer` 與 `qa-lead` 各自獨立發現此矛盾）。若後段判定時已超過時效，只以敵人原生 `BaseAttribute` 計算剋制（可能無剋制）——**這是連攜技設計時必須自我保證的約束**（見 gem-socketing.md）。
- **同一敵人被兩個不同連攜領域的階段1先後賦予不同屬性**：後者覆寫前者，時效重新計算（沿用 gem-socketing.md 既有規則，本 GDD 不重新定義）。
- **連攜的屬性賦予可能讓玩家自己的塔剋制窗口變差**（本輪修訂新增）：`AppliedAttribute` 對 gem-socketing 是完全覆寫。例如「炎寒領域」把範圍內敵人染成霜屬性後，玩家自己的雷塔在時效內對這些敵人變成 `AffinityMult = 0.75`（霜剋雷）；若敵人原生 `BaseAttribute` 是火，染霜也會讓蝕塔原有的 ×1.5 視窗關閉。**這是刻意接受的負面協同**，不額外處理或提示——玩家透過符文變化（見 Visual/Audio Requirements）觀察到剋制關係改變，屬於「讀懂戰場」的一部分。
- **參與塔在施法模式（Aiming）期間被拆除或進入破損狀態**：不立即取消目前的施法模式。落點圓在進入 Aiming 當下即鎖定快照（座標與半徑），後續塔的狀態變化不回溯影響已鎖定的圓。本輪修訂新增：但**前搖完成、即將生成效果實例的那一刻，會重新驗證配方**（規則3的簡化版：僅確認快照中的參與塔目前是否仍存在且仍持有原屬性）。**第2輪修訂（原判定為進入 ShortStun，經 `systems-designer` 覆核後修正）**：驗證失敗時，玩家沒有移動、沒有受擊，是一個玩家完全無法反制的事件（材料被場上其他因素移除，不是玩家的操作失誤）——這與 `ShortStun` 代表的「賭輸前搖」精神不同，改採**規則7同等的無代價取消**：回到 `Idle`，不進 CD、不消耗任何資源，廣播 `OnChainInterrupted` 並攜帶第四種原因標記 `MaterialInvalidated`（材料失效，區別於移動取消／受擊取消／前搖被打斷，見 AC53 與 Visual/Audio Requirements 的專屬視覺語言：杖光熄滅＋參與塔高亮消散，不使用踉蹌動作，避免玩家誤判為「我被打了」）。這避免了「用不存在的材料生成效果」與 game-concept「塔是材料」不變式的矛盾，也讓 Visual Requirements 中效果實例生成瞬間的杖→塔光束永遠有真實目標可指。**破損但未被拆除／未被取下寶石的塔**在此驗證中視為仍然有效（破損不影響材料資格，只影響該塔自身的攻擊輸出）。
- **「星星之火」左鍵確認時準心未命中任何敵人的 hit box**：**仍依 Core Rules 規則6正常進入前搖**（左鍵確認不判定是否命中，只判定落點——與其他連攜技一致，且依規則12於確認當幀鎖定目標快照），前搖完成後正常生成效果實例並消耗 CD；差別只在於 Phase 1 的點燃效果因未命中目標而**不生效**（不產生火種標記），Phase 2 因此永不觸發，並由規則10的 `MaxActiveDuration` 強制結束該效果實例。**打空與命中消耗相同的 CD 與資源，沒有免費重試**——這是「星星之火允許精準瞄準、換取遠距離精準點燃」的代價之一（見 Core Rules 規則9、12，Visual/Audio Requirements 的瞄準鏡例外聲明）。
- **對已有「火種」標記的敵人再次施放「星星之火」階段1**：覆寫並重置 `EmberDuration`（8秒）倒數計時，不疊加多個火種。
- **「凍土」定身的敵人受到擊退類效果**（如風塔攻擊）：**免疫位移，只受傷害不受位移**，避免「定身」與「擊退」兩種位置狀態互相矛盾。
- **巫師在 Aiming／Windup／ShortStun 期間死亡**（本輪修訂新增，第2輪修訂移除 Active——見規則11 說明，`Active` 已收斂為單幀轉場）：見 Core Rules 規則11。
- **三個 MVP 連攜技同時皆在冷卻中**：非死局。基礎塔（含已嵌合寶石之塔）的攻擊持續正常運作，不受連攜技可用性影響——連攜是加成手段，不是防守成立的必要條件（呼應 gem-socketing.md「基礎塔仍具攻擊能力」）。
- **玩家整關的寶石配置湊不出任何一個連攜技的配方**（本輪修訂新增）：屬於出戰配置與掉落隨機性的交互，不在本系統職責範圍內解決；已登記為 Open Question（見文末），須與 gem-socketing 的關卡資料驗證規則對齊。
- **準心射線未命中任何目標平面**（第2輪修訂新增，修正阻擋性洞）：玩家把準心指向天空、地圖邊界外的虛空、或任何沒有碰撞體的方向。此時候選落點**維持上一個有效值**（不更新）；由於規則5規定「進入 `Aiming` 的當下落點立即初始化為 `CastCircle` 圓心」，候選落點恆有初始值，因此「上一個有效值」不可能是未定義狀態。
- **`AttackRadius` 為 0 或未填**（第2輪修訂新增）：比照 `ChainDomainRadius` 的 `K > 0` 先例，`AttackRadius` 須有資料驗證下限 `> 0`（須由塔系統的資料規格保證，本系統無法在自己的資料層驗證上游欄位，僅在此登記需求）。若上游未驗證而允許 0，`CastCircle` 半徑會被夾成 0，落點永遠鎖死在圓心，瞄準完全無效且無任何錯誤提示——這與 `K = 0` 想防範的靜默失效是同一類問題。

## Tuning Knobs

| 旋鈕 | 預設值 | 太高會怎樣 | 太低會怎樣 |
|---|---|---|---|
| `ChainDetectionRadius` | 6 公尺（provisional） | 感應範圍過大，站位不再是限制條件，違背支柱②「站位就是資源」| 感應範圍過小，玩家難以同時涵蓋兩座塔，連攜難以觸發 |
| `ChainDetectionRadiusHysteresis`（第3輪新增） | 0.4 公尺（provisional） | 遲滯帶過寬，玩家會感覺塔「黏」在配方裡明明已經走遠卻還算數，感應範圍變得不可預測 | 遲滯帶過窄，起不到去抖動作用，技能列在邊界附近閃爍（見規則3） |
| `ChainTickDamageMult`（第3輪：由 `ChainDamageMult` 拆分）| 0.5（provisional）| 領域類連攜的持續傷害蓋過塔本身輸出，違背「巫師輸出弱、塔是主力」的核心設定 | 領域類連攜變得純粹是「賦予屬性」的工具，火海/熔岩階段感受不到威力 |
| `ChainBurstDamageMult`（第3輪新增）| 2.5（provisional）| 星星之火變成最優解、擠掉另兩招的使用時機，且會讓反支柱③豁免顯得像在獎勵操作技巧 | 星星之火重新落回被支配（見 Formulas 的推導）：付出瞄準成本與打空風險卻拿不到相稱回饋 |
| `PhaseTickInterval`（第2輪修訂新增） | 0.5 秒（stub） | tick 太密集，`ChainTickDamageMult` 疊加後總傷害失控，須連動調低——**且會同時破壞與 `ChainBurstDamageMult` 的等效總量平衡**（第3輪補充） | tick 太稀疏，領域效果的持續壓力感消失，玩家會覺得站在領域裡沒有意義 |
| `ChainSkillCooldown` | 30 秒 | 技能幾乎不可用，玩家會放棄站位規劃 | 連攜變成可以隨時spam的常態操作，稀釋支柱①「配置勝於操作」——決策重量從「何時放」退化成「盡量放」|
| `MaxActiveDuration`（第2輪修訂新增） | 逐技能宣告（星星之火 8.5s／炎寒領域・凍土 4.5s，皆 stub） | 效果實例拖太久才強制結束，若愈調愈接近 `ChainSkillCooldown` 會有兩實例重疊風險（見不變式，Formulas 節） | 效果實例被腰斬過早，尚未自然結束的階段（如引爆判定窗）沒機會發生，技能感覺「沒打完」 |
| `ShortStunDuration` | 1.0 秒（provisional，第2輪修訂由 0.5 秒上調以對齊 art-bible §5 踉蹌動畫規格） | 賭輸的代價過重，玩家會過度保守、不敢在怪群中冒險施放 | 賭輸幾乎沒有代價，前搖的「風險」名存實亡；亦不可低於踸蹌動畫演完所需時長（見 Formulas 節） |
| `ChainDomainRadius`（K，待定）| 待原型驗證 | 涵蓋範圍過大，站位不再是限制條件，違背支柱②「站位就是資源」；若接近或超過 `CastCircle` 半徑，兩個地面圓會難以視覺區分 | 範圍過小，敵人密度不足時連攜打不到人，變成不可用的裝飾機制 |
| `EmberDuration` | 8 秒 | 「火種」幾乎不會過期，玩家不需要規劃風塔配置的時機，佈局型設計退化 | 過短導致風塔剛好命中的機率太低，「延遲引爆」變成靠運氣而非佈局判斷；亦需維持不超過 `MaxActiveDuration`（見 Formulas 節，第2輪修訂：不變式對象已由 `ChainSkillCooldown` 更正為 `MaxActiveDuration`） |
| `AppliedAttributeDuration_炎寒領域` | 4.5 秒 | 時效過長，容易與其他連攜領域的屬性賦予重疊，產生非預期的連鎖剋制 | 低於 4.5 秒有卡在階段2判定臨界的風險（見 Edge Cases 的臨界推導），階段2剋制判定可能失效 |
| `CastWindup` | 0.3 秒（game-concept 不變式，**鎖定值**——改動須回頭修改 game-concept） | 前搖過長會讓連攜在怪群密集時手感遲鈍，違反 `CastModeDwellBudget` 精神 | 過短會讓「可被打斷」窗口形同虛設，前搖存在的風險/賭注感消失 |
| `CastModeDwellBudget` | ≤1.0 秒（設計驗證基準，非計時器） | — | 若原型實測顯示玩家平均反應時間超過此值，需要 hover 預覽等緩解方案（見待解問題#3） |

**旋鈕間的交互**：兩個傷害係數皆與 gem-socketing 的 `AffinityMult`(剋制 1.5／被剋 0.75) 疊乘——調整前須注意，剋制本身被 gem-socketing 定案為「調味不是主菜」，連攜傷害的份量不該靠疊加剋制倍率來彌補，應直接調整係數本身。**`ChainTickDamageMult` 與 `ChainBurstDamageMult` 必須一起看**：兩者的**每次施放等效總量**（tick 型 = 係數 × tick 數；爆發型 = 係數 × 1）應維持在同一個量級，否則其中一類技能會被另一類支配——這正是第3輪修訂拆分它們的原因，單獨調整任一個都會重新打開那個洞。`ChainSkillCooldown` 與傷害係數／`PhaseTickInterval` 是一組蹺蹺板：CD 越短則每次施放的等效總量應越低，避免兩者同時偏高造成連攜輾壓一般塔輸出。`MaxActiveDuration` 必須恆小於 `ChainSkillCooldown`（第2輪修訂，見 Formulas 節說明）；`EmberDuration` 必須不超過其所屬技能的 `MaxActiveDuration`。

## Visual/Audio Requirements

> 注：本系統屬於視覺必要類別（驅動 VFX 系統 #23、動畫系統 #33、連攜技能 UI #21）。本節初稿由主對話依 art-bible 既定規格草擬；本輪 `/design-review`（full 模式，2026-09-22）另由 `art-director` 執行了一輪獨立對抗式覆核，發現數項問題（雙圓同時存在、瞄準鏡與反支柱③的矛盾、第一人稱視角缺口等），已於下方處理。

### 狀態轉換的視覺回饋

**Idle → Aiming（施法模式）**
巫師切換為 art-bible §5 姿態庫定義的「連攜・施法模式」姿態：**法杖向下插於身前、雙手握杖中上段**。此姿態與「建造／嵌合」姿態（法杖向上高舉、單手）必須在**純黑剪影下可分**——上 vs 下、單手 vs 雙手為主要區分依據。此為安全資訊：兩者的受擊後果完全相反（建造不中斷、Aiming 立即取消），看混會被感受成遊戲不公平。
腳下同步浮現**節點環**作為「我現在不能動」的持續指示。節點環**不得沿用黃黑斜紋施工光環**（§5 明令），須為另一套圖樣語彙（具體圖樣待 `/asset-spec` 定案）。
音效：短促的「杖尖點地」起手音，低音量、可被戰鬥音蓋過——此階段非 Peak（§2）。

**Aiming 狀態的落點預覽**
依 §7「技能列＋落點圓」規格：可釋放圓為地面實心邊界圓（圓心與半徑於進入 Aiming 當下鎖定快照，見 Edge Cases）；參與塔以屬性色輪廓**加上該塔上方／輪廓附屬的屬性符文**高亮，明確傳達「這幾座是材料」（**第2輪修訂，`art-director` 覆核發現的阻擋性缺口**：原版本只用屬性色輪廓單一層區分，但 art-bible §7 明文把符文複用延伸到「塔的狀態指示」與「連攜落點圓」，§4 色盲安全段落更點名火×風正是最高風險的色彩碰撞組合，需要「符文＋明度」兩層區分——僅色輪廓只提供一層。符文是強制項，不是備援，避免色盲玩家在「火＋風」配方下無法分辨兩座參與塔各自對應哪個屬性）；準心落點標記顯示領域實際覆蓋範圍（`ChainDomainRadius`，非落點圓大小，兩者尺寸差異須一眼可分——**須維持明顯的最小尺寸比例**，若原型實測顯示兩圓過於接近，須回頭調整 `ChainDomainRadius` 的建議上限，見 Formulas 節）。腳下節點環、落點圓、領域預覽三者同時出現於 Aiming 期間時，須以**形態**而非僅尺寸區分（例如落點圓為連續實心邊界、領域預覽為填充面、節點環為分段弧），具體圖樣待 `/asset-spec` 定案，此處僅約束「不得三者皆為細線圓環」。
**貼齊圓周邊緣**時（Acceptance Criteria），落點標記須有**吸附感回饋**（極短形變或邊緣微光）＋一次輕微的滑動音，讓玩家知道「輸入沒被拒絕，只是被限制住了」——若無回饋，玩家會誤判為卡住。標記轉為不可用樣式時**不得使用紅色**（§4「紅色問題」）。
**禁止**任何塔與塔之間、巫師與塔之間的持續光帶或連線效果（見 art-bible §7 光束預設規則；例外須由技能自身策略定義宣告，見 Core Rules 規則9）——鏈路模型已作廢，畫線會暗示一個不存在的機制。

**施法流程的五種非完成結束態 → 收斂為三套視覺語言**（第3輪修訂：由「五種語言互異」收斂為「五個事件標記 ÷ 三套表現語言」）

> 📌 **第3輪修訂的裁決（`art-director` 與 `qa-lead` 意見相左，由 `creative-director` 裁決）**：
> `qa-lead` 論證現行規格自洽（移動取消只發生在 `Aiming`、材料失效只發生在 `Windup` 完成瞬間，兩者不會在同一狀態出現，故混淆風險低於表面），判定可接受。`art-director` 則指出這是在回答「規格自洽嗎」（文件問題）而非「玩家需要這個區分嗎」（遊戲問題）——**受擊取消不需要專屬視覺語言，因為玩家早已透過血量變動、擊退位移、全螢幕受擊回饋知道自己被打了，那些通道與連攜系統無關且一定存在**；為它再造一套等於重複一個已經更大聲的訊號。
> **裁決：採 `art-director` 的方向，但不採其「兩軸」提案**——踉蹌必須保持獨立，因為它是唯一有時長、唯一有代價的結束態，收掉它玩家就學不會前搖的風險模型。

> | 事件層 reason tag（**保留全部五種**） | 視覺／音效語言（**收斂為三套**） |

> | `MovementCancel`／`HitCancel`／`MaterialInvalidated` | **① 無代價取消**（中性收回語言） |
> | `WindupInterrupted` | **② 踉蹌**（唯一有代價者） |

> **事件層維持五種標記**（決策：使用者於第3輪明確選擇）——標記本身便宜、可自動化測試，且三星挑戰與 UI 日後可能需要區分取消原因；收斂的只有美術／音效工單，由五套降為三套。

> **但 `MaterialInvalidated` 必須攜帶失效的塔實例 ID**（第3輪新增，`art-director` I1 的核心洞察，`qa-lead` 未觸及）：現行規格要求「參與塔高亮消散」——齊頭式地全部消散，於是玩家知道「有材料沒了」卻不知道**是哪一座**。而整套分類法的正當性理由是「否則無法學習風險模型」；「某處某座塔沒了」既不可學習也不可行動，「那座火塔被拆了」才是。**表現規則**：失效的那一座做出與其餘參與塔**明顯不同**的熄滅（塌陷／碎裂），其餘正常消散——資訊載體是**參與塔高亮**，不是巫師姿態，成本也更低。事件 payload 須含該塔 ID，見 AC53。

**玩家實際需要分辨的是三類學習結論**（第3輪修訂：原文宣稱「玩家必須分辨發生了哪一種」五選一，現收斂）——「我沒付出代價，重來就好」／「我賭輸了，這一秒不能動」／「我換招了」。**只有第二類有代價，因此只有它需要一套不可錯認的專屬語言**；第一類三種成因共用中性收回語言即可，因為玩家的行動結論相同（重新站位再放一次），差異資訊由 `MaterialInvalidated` 的失效塔高亮承載，而非由巫師姿態承載。

**Windup（0.3 秒）——可見的賭注**
前搖不可只是播動畫。杖身須有**可見的蓄能爬升**（亮度在 0.3 秒內單調上升，**第2輪修訂：上限收緊為「落點圓與塔輪廓」一級**，原「危急塔透光」上限過寬——Windup 正是玩家盯著落點與參與塔確認的時刻，不該讓杖身亮度蓋過那兩者；張力改由**形變與時間曲線**承擔，不靠亮度堆疊），使玩家在被打斷時感知到「差一點就成了」。依 §2，此階段**亮度維持一般水準，不屬於 Peak**。音效為上揚的 0.3 秒充能音，被打斷時**戛然截斷**（不做淡出）。

**效果實例生成瞬間——Peak（§1 原則③，第2輪修訂：原標題「Active 起始瞬間」已隨三層模型更名，指的是規則8同幀事件中「效果實例生成」的那一刻，不是一個持續的全域狀態）**
全畫面亮度與動態最高點，0.3–0.5 秒，不可拖長：光自法杖射向**參與塔**（唯一允許的杖→塔光束，僅此瞬間存在，見 art-bible §7）——**前搖完成時已重新驗證參與塔仍然存在**（見 Edge Cases），此光束永遠有真實目標可指。領域於落點展開。玩家視線若未被自動吸引過去即為不合格（§1 設計測試）。
> ⚠️ **光束起點必須是世界座標快照，不可 parent 到法杖骨骼（第3輪修訂新增，阻擋性，`art-director` 覆核發現）**：這是三層模型重構的直接副作用，視覺節先前只改了標題卻沒處理後果。規則8 修訂後，巫師在**效果實例生成的同一幀**就恢復移動——而玩家在怪群裡放完連攜的第一反應就是跑。若光束起點跟著法杖 transform，這道 0.3–0.5 秒的光要嘛被拉成荒謬的長度、要嘛在播放中途斷開，而它正是整個系統最高潮的那半秒。
> **規則**：光束起點於效果實例生成當幀**快照為世界空間座標**（取當幀杖尖位置），之後不隨巫師移動。語意上也更正確——這道光表達的是「材料已被消耗」這個**已發生的事件**，不是巫師持續在輸出。art-bible §5「杖尖是所有動作的光源與起點，玩家視線有固定錨點」的設計理由在此仍成立：錨點固定在事件發生的位置，而不是固定在一個會跑走的物件上。
**隨後亮度必須回落**至一般高飽和魔法層級，維持 §7 完整六層亮度階層：連攜領域生成瞬間 ＞ 危急塔透光 ＞ 連攜領域持續期 ＞ 落點圓與塔輪廓 ＞ 受損塔透光 ＞ 一般寶石光（**第2輪修訂**：原版本誤引為 4 層，漏列後兩層；本節新增的節點環、火種標記、符文替換閃光、吸附感邊緣微光、Windup 蓄能五個元素，各自的位階為：Windup 蓄能≤落點圓與塔輪廓（上方已收緊）；節點環＝落點圓與塔輪廓同級；火種標記＝連攜領域持續期同級；符文替換閃光、吸附感邊緣微光＝受損塔透光同級，皆為短暫的低強度提示，不得與 Peak 同級）。
音效為全曲最強的一次擊發音，須高於戰鬥混音層；領域持續期轉為低音量環境層。

### 領域與標記的持續視覺

**階段切換（炎寒領域 暴風雪 → 火海）**
依 §2、§4 硬性要求：切換須為**明確的形變或閃光事件**，不可只改色相——色盲玩家必須看得出「暴風雪變成火海了」。領域屬性另以**脈動頻率**區分（火慢、雷急促），且此脈動頻率須與 §4 危急語意的白色高頻脈動明顯區隔（第2輪修訂新增：避免玩家把「這個領域是雷屬性」誤讀為「有東西快死了」——危急語意用無色相的白色脈動，資訊語意一律用屬性色脈動，兩者不共用頻段）。切換給一次獨立的轉場音，與 Peak 音可分。

**屬性賦予／覆寫**
沿用 §5 敵人屬性符文規格：`AppliedAttribute`（連攜賦予，4.5 秒時效）＝符文外加**跑動虛線框**，時效將盡時**加快閃爍**；`BaseAttribute` 為靜態貼合符文。被另一領域覆寫時，須有一次**符文替換閃光**，讓玩家知道剋制關係已改變（見 Edge Cases：覆寫且時效重算）。**第2輪修訂新增（阻擋性，`art-director` 覆核發現）**：領域對範圍內全體敵人同時呼叫屬性賦予時（例如「炎寒領域」暴風雪階段對一波怪同時觸發覆寫），符文替換閃光**須設聚合上限**——同一幀內多隻敵人的替換閃光合併為一次區域級、低強度的提示，個體閃光不逐一疊加亮度，避免大量敵人同時被覆寫時，這個原本只是「受損塔透光」等級的小提示，聚合成一個蓋過 Peak 的全畫面事件。

**火種標記（星星之火）**
須為敵人本體上的持續、可從中遠距離辨識的標記（§5 LOD 哲學：投資輪廓與發光，不投資材質）。剩餘時間以**離散階段（如 3 段式環形進度）**表達，**不採用「衰減亮度或收縮形狀」**（本輪修訂：原方案會讓標記在最需要被看清的到期前變得最暗/最小，與「可從中遠距離辨識」的要求自相矛盾）；`EmberDuration` 將盡時加快環形進度的閃爍頻率——玩家要靠它判斷「風塔還來不來得及」。火種不得改變敵人本體顏色（§5，敵人本體固定 ≤30% 飽和）。引爆為小型 Peak，強度須**低於**連攜生成瞬間、**高於**危急塔透光，不搶 §7 亮度階層。

**星星之火的瞄準鏡效果**

> ⚠️ **例外聲明（第2輪修訂：由「隱性例外」改為「正式擴大支柱豁免範圍」）**：第1輪 review 的版本把這個例外寫成「刻意的單一例外，不影響反支柱③是否成立」——但 `art-director` 與 `creative-director` 在第2輪對抗式覆核中指出：game-concept §3.2 只明文豁免了 `CastCircle` 的**區域式目標選取**（星星之火改為單體遠距離目標），從未豁免「一律透過準星＋自動吸附完成，不要求精準對位」這條適用於**所有**目標選取方式的硬性操作前提。本節先前的寫法等於把「效果範圍的例外」悄悄升級成「操作技巧的例外」，卻仍宣稱「多數連攜技無瞄準」（Player Fantasy 節）成立、反支柱③未被違反——這是自我矛盾的表述，而非真正解決了矛盾。
>
> **使用者在本輪修訂中明確決定**：保留星星之火的自由瞄準玩法（不採用「自動吸附鎖定遠距離目標」的重新框架方案），並承認這是對反支柱③（不做操作技巧門檻）**正式且刻意擴大的豁免**——不再以「例外不影響支柱是否成立」的方式輕描淡寫。本文件因此：
> 1. **回頭修改 game-concept.md §3.2**，將反支柱③的豁免範圍明文擴大為「星星之火同時豁免區域式目標選取與精準對位操作前提」（見 game-concept.md 的對應修訂）——豁免範圍寫在支柱層級的文件裡，不是只藏在系統 GDD 的一句註解中。
> 2. **此豁免僅限星星之火一個技能**；若日後（v1.0 擴充連攜技時）出現第二個需要精準瞄準的技能，須回頭重新評估反支柱③在整體遊戲中的地位是否仍然成立，不可默默增加例外數量——這個限制維持不變。
> 3. **保留的擴充可能性**：若原型測試顯示這類「精準遠距離目標」的操作模式受歡迎，v1.0 可考慮將其提升為一個正式的、有限使用的技能子類別（而非一次性例外）——但那屬於 v1.0 規劃範圍，MVP 維持單一例外。
> 4. 理由（維持不變）：星星之火的核心動詞是「遠距離精準點燃」，這是三個技能裡最貼近核心動詞「接通」的一個；改用自動吸附會削弱這個定位。

「星星之火」不受落點圓約束、目標為單一遠距離敵人（見 Core Rules 規則9 的逐技能宣告），Aiming 狀態下視野收窄為基準 FOV 的 **1.5 倍放大鏡效果**（即實際視角縮小為基準 FOV 的約 1/1.5，畫面呈現為「放大」，第三人稱與第一人稱須分別定義各自的基準 FOV 與呈現方式；第三人稱下是否伴隨鏡頭前推／重新定位，待 `/ux-design` 定案），區別於落點圓技能（炎寒領域／凍土）的正常視野瞄準。**這是會打空的判定，且打空一樣進 CD**：左鍵確認一律正常進入 Windup（規則6對所有技能一致），前搖完成後消耗 CD；hit box 只決定 Phase 1 的點燃效果是否生效（見 Edge Cases），不影響流程本身。瞄準鏡收起時機與退出 Aiming（含正常前搖／被打斷／CD消耗後）同步，不可有額外延遲（≤1 frame）；務必讓玩家清楚感知到「這一鏡打出去了」而非卡在瞄準狀態，避免誤以為未消耗資源——**若瞄準鏡在 Windup 期間仍需維持顯示以呈現「已確認，正在蓄力」的狀態，須額外定義瞄準鏡下的蓄能視覺變體，待 `/ux-design` 補齊**。

> ⚠️ **第一人稱視角下的姿態辨識缺口（本輪 `/design-review` 修訂新增，待 `/ux-design` 解決）**：本節的 Idle/Aiming 姿態區分、上述結束態的動作差異，皆假設玩家看得到巫師全身——但 art-bible §5 明訂第一人稱只顯示手部與法杖前端，且第一人稱已確認納入 MVP。**這是一個尚未解決的缺口，不是本節遺漏**。**第2輪修訂：部分現在可定案，不必全部留給 `/ux-design`**：① 技能列上的鎖定樣式（ShortStun 的持續指示）是螢幕空間元件，第一人稱與第三人稱共通，不需要另外設計；② 落點圓在第一人稱下按 §7 規格「邊界加粗」處理部分畫面外內容，但本節 UI Requirements 原本禁用邊緣指示器——此處正式新增**窄例外**：落點圓（僅此一項）超出畫面的部分可用**靜態、不脈動**的貼邊弧段表示，靜態語意與 §7「邊緣指示器僅保留給緊急事件（脈動語意）」的精神不衝突；③ 節點環的外緣半徑須確保其前方弧段在第一人稱預設俯仰角下落於視錐內（純幾何約束，不涉及色彩或像素值）。**第3輪修訂：通道歸屬現在就在 GDD 定案，不再整批推給 `/ux-design`（阻擋性，`art-director` 覆核發現）**
`art-director` 指出先前的推遲是**分類錯誤**——被推走的不只是像素值與圖形方案（那確實是 UX），還包括「哪個狀態由哪個通道承載」這個美術方向決策。盤點第一人稱下五種結束態的存活率後，發現一個不可接受的缺口：

| 結束態 | 第三人稱載體 | 第一人稱是否存活 |
|---|---|---|
| 搶佔 | 技能列焦點轉移＋參與塔高亮重播 | ✅ 螢幕空間＋世界空間皆在 |
| 移動取消 | 圓瞬消＋乾淨收招姿態 | ⚠️ 只剩圓 |
| 受擊取消 | 同上＋方向性受擊提示 | ✅ 受擊提示是全遊戲通用通道，非連攜專屬 |
| 材料失效 | 杖光熄滅＋高亮消散 | ✅ 杖尖光是第一人稱最可靠的通道 |
| **`ShortStun`** | 踉蹌動作＋技能列鎖定 | ❌ **踉蹌全滅；技能列在螢幕底部，而第一人稱玩家正盯著遠方** |

**唯一有時長、唯一代表「你賭輸了、這一秒不能動」的狀態，在第一人稱下完全沒有落在玩家視線裡的載體**——而它的救援方案（鏡頭失衡）先前不只被推遲，還預先宣告「可由玩家關閉」，關閉後的保底正是那個看不到的技能列。懲罰讀不到 ＝ 前搖的風險模型學不會 ＝ 規則8 整段白寫。

**因此本輪鎖定通道歸屬表（圖形方案與像素值仍屬 `/ux-design`）**：

| 狀態／結束態 | 第一人稱主載體 | 備註 |
|---|---|---|
| **`Aiming` 進行中** | **準心樣式變化**（新增，見下方說明）＋落點圓 | 準心是唯一保證落在第一人稱玩家凝視點上的元件 |
| **`ShortStun`** | **準心散開／失效樣式，持續完整 1.0 秒** ＋杖尖光破碎 | **不可關閉的保底**；鏡頭失衡降為可關閉的加味，而非唯一方案 |
| 移動取消 | 圓瞬消＋杖尖光**淡出** | |
| 材料失效 | 杖尖光**塌陷**（不同曲線，非淡出）＋失效那一座塔的高亮單獨熄滅 | 與上一行靠曲線形態區分，不靠亮度 |
| 「我不能動」的持續指示 | **準心底部的固定鎖定標記**，取代腳下節點環 | 節點環在第一人稱下不可靠——它最該生效的場景（星星之火瞄遠方敵人）玩家正抬頭平視，腳下環 100% 出框 |

> 📌 **準心正式被認領為第一人稱主載體**——先前全文只在待解問題 #5 含糊帶過，從未指派任何狀態給它。這四條是美術方向決策，不是介面排版；`/ux-design` 承接的是它們的圖形方案。

**仍留給 `/ux-design` 的**：準心各樣式的實際圖形方案、踉蹌在第一人稱下的鏡頭語言細節（作為準心保底之上的可關閉加味）、落點圓加粗的實際像素值（見下方待解問題清單）。在此之前，第一人稱下的連攜狀態辨識視為**未驗證**，`/prototype --spike` 應包含第一人稱情境。

> **本節服務的 art-bible 原則**：① 厚重的世界，明亮的魔法（領域與杖光為高飽和魔法層，塔與敵人本體維持低飽和退後）、③ 連攜是畫面上最亮的東西（效果實例生成瞬間的 Peak 與六層亮度階層）。
> **服務的支柱**：②站位就是資源——玩家付出站位換來連攜，回饋必須是全畫面最強的訊號；落點圓、參與塔高亮與三種失敗態的差異化，共同使「站位的代價與收益」在戰鬥中可被即時讀取。

## UI Requirements

> 注：本機未安裝 `ux-designer` agent 檔案——本節由主對話依 art-bible §7 既定規格與 Interactions with Other Systems 表中已列的 UI 資料需求直接草擬，未經 UX specialist 諮詢。**正式製作前必須執行 `/ux-design`**（見文末 UX Flag）。

### 資料介面（連攜系統對外提供，UI 系統負責繪製）

連攜系統本身不畫任何 UI，只透過事件匯流排與唯讀查詢對外提供以下資料（呼應 Interactions with Other Systems 表）：

| 資料 | 用途 | 更新時機 |
|---|---|---|
| 各技能的可放性旗標（bool） | 技能列圖示全亮／灰化 | 每次巡邏移動後即時重算（規則3） |
| 配方缺口（缺哪個屬性、缺幾座） | 灰化狀態下的符文提示 | 同上 |
| 各技能 CD 剩餘 | 技能列環形進度 | Cooldown 狀態期間持續 |

### 已知的 UI 元件需求（承接 art-bible §7，非本節新定義）

- **技能列**（螢幕下方，常駐）：可施放／配方不足／CD 中三態，見 art-bible §7「技能列＋落點圓」。
- **落點圓**（世界空間，Aiming 期間才出現）：可釋放圓、參與塔高亮、準心落點標記、圓外不可用樣式。
- **邊緣指示器**：技能列與落點圓皆為主動查看／預期內資訊，**不使用**邊緣指示器（該元件依 art-bible §7 僅保留給緊急事件，如塔危急或敵人從背後接近，與連攜系統無關）。

## Acceptance Criteria

> 注：本節屬於高風險章節（H）。**本輪 `/design-review`（full 模式）由 `qa-lead` 對抗式覆核，判定文件開頭原先聲稱的「已量化模糊用詞」不實**（AC17/18/25 仍殘留「立即」「不受影響」等未量化字眼），且約 20/41 條原 AC 不可獨立測試。以下為修訂後的完整版本，取代原版本的編號。

1. GIVEN 巫師站位使某屬性塔的數量 < 配方需求，WHEN 玩家按下對應技能鍵，THEN 狀態仍為 Idle、`IsInCastMode()` 回傳 false、該技能 CD 值不變、未廣播 `OnChainAiming`。

3. ⚠️ GIVEN 巫師站位 (0,0,0)、配方需求火×1，範圍內恰有一座已嵌合火寶石的塔於 (2,0,0)（`AttackRadius` = 4，依賴塔系統，見 Dependencies），WHEN 玩家按下對應技能鍵，THEN 同一幀內進入 Aiming 狀態，`IsInCastMode()` 回傳 true，`CastCircle` 圓心 = (1,0,0)（±0.001，由 centroid 公式手算）、半徑 = 4（±0.001），且初始落點等於圓心 (1,0,0)（**第2輪修訂**：原斷言「等於快照值」為套套邏輯，改為手算具體數字，避免拿被測邏輯的輸出驗證自己）。
4. GIVEN 巫師已在 Aiming 狀態，WHEN 玩家按下另一個**已解鎖、不在 Cooldown 中、配方也滿足**的技能鍵，THEN 同一幀內取消原技能 Aiming（CD 不變、資源不變）並切換為新技能 Aiming，落點圓同幀更新為新技能的快照值，且同幀廣播 `OnChainInterrupted(Preempted)` 供訂閱方區分「搶佔」與其他三種結束態（見 AC54）。
5. GIVEN 巫師已在 Aiming 狀態，WHEN 玩家按下一個**正在 Cooldown 中**的技能鍵（即便其配方目前滿足），THEN 該幀結束時：全域狀態仍為 Aiming、`currentSkillId` 不變、`CastCircle` 圓心／半徑與按鍵前相等（±0.001）、未廣播 `OnChainAiming` 或 `OnChainInterrupted`、被按下的技能之 CD 剩餘不變（±0.001）（**第2輪修訂**：原「不受影響」改為逐項可驗證斷言，驗證規則2的搶佔條件包含 CD 檢查）。
6. GIVEN 巫師已在 Aiming 狀態，WHEN 玩家按下**目前正在 Aiming 的同一個技能**的鍵，THEN 視為 no-op，落點圓不重取快照、圓心與半徑維持原值。
7. GIVEN 巫師處於 Windup 或 ShortStun 狀態，WHEN 玩家按下任一技能鍵，THEN 輸入被忽略，狀態不變（**第2輪修訂**：`Active` 已收斂為單幀轉場，不再是一個會被按鍵測到的持續狀態，見規則8）。
8. GIVEN 技能列順序以測試 fixture 注入為 `[A, B]`，兩個技能鍵於同一幀內被偵測到且皆滿足配方（以固定輸入注入測試重現），WHEN 依技能列順序判定，THEN A 進入 Aiming，B 的輸入未產生任何狀態變化或事件廣播。

### 配方比對與參與塔篩選（規則3/4）

9. GIVEN 場上無任何已嵌合塔，WHEN 按下任一技能鍵，THEN `ChainDetectionRadius` 查詢回傳固定值 6（±0.001），配方分組結果為空，狀態仍為 Idle。
10. GIVEN 某屬性塔數量恰好等於配方需求數，WHEN 配方檢查執行，THEN 判定為滿足（非不足）。
11. GIVEN 某屬性塔數量為 0，WHEN 配方檢查執行，THEN 判定為不滿足，不進入 Aiming。
12. GIVEN 某座塔與巫師的距離恰好等於 `ChainDetectionRadius`（6 公尺），WHEN 配方檢查執行，THEN 該塔納入範圍（含邊界）。
13. GIVEN 配方要求兩種屬性，其中一種數量不足、另一種充足，WHEN 配方檢查執行，THEN 整體判定為不滿足。
14. GIVEN 某屬性符合的塔數量超過配方需求 N，WHEN 配方檢查執行，THEN 參與塔清單恰為距巫師最近的 N 座，其餘同屬性塔不參與 CastCircle 計算。
15. GIVEN 兩座同屬性塔與巫師距離相等且並列第 N 名候補，WHEN 篩選執行，THEN 依塔的唯一實例 ID 升序排序決定較小 ID 者入選，結果可重現、非隨機（以具體塔 ID 指定預期入選者）。
16. GIVEN 配方資料結構定義為某屬性 ×2，WHEN 篩選邏輯執行，THEN 能正確篩出距巫師最近的 2 座該屬性塔（以具體座標指定預期的兩座塔 ID，驗證資料結構的可擴充性，即便 MVP 未使用）。

### 狀態機轉移（三層模型，第2輪修訂：由兩層改為三層，見 States and Transitions）

17. GIVEN 巫師處於 Aiming 狀態且落點在 CastCircle 內，WHEN 玩家按下左鍵確認，THEN 同一幀進入 Windup；t < 0.3 秒時狀態維持 Windup，t ≥ 0.3 秒（未受打斷）時全域狀態機同幀轉入 Idle 且生成一個新的效果實例（±1 frame，驗證規則8：Windup 不再轉入一個會持續的 Active 狀態）。
18. GIVEN 巫師處於 Aiming 狀態，WHEN 玩家的移動軸輸入超過巫師能力系統的死區閾值，THEN 同一幀返回 Idle，不進 CD，不消耗資源，`IsInCastMode()` 同幀轉為 false，巫師該幀位移量為 0（±0.001，驗證取消判定早於移動積分，規則7）。
19. GIVEN 巫師處於 Aiming 狀態，WHEN 巫師受到一次離散且傷害 > 0 的攻擊，THEN 同一幀返回 Idle，不進 CD，不消耗資源；WHEN 巫師處於 Aiming 狀態且僅受到持續傷害（DoT tick）或傷害為 0 的效果，THEN 不觸發取消，狀態維持 Aiming；WHEN 巫師處於 Aiming 狀態且移動軸輸入超過死區、同一幀又受到離散攻擊，THEN 僅廣播一次 `OnChainInterrupted`（不因兩個取消條件同時成立而重複觸發）。
20. GIVEN 巫師處於 Windup，WHEN 前搖期間受到攻擊（定義同規則7），THEN 進入 ShortStun，技能不進 CD；WHEN `ShortStunDuration`（見 Tuning Knobs）經過，THEN 狀態轉為 Idle（±1 frame），該技能可用性維持 Ready（未進 CoolingDown）。
20a. GIVEN 巫師處於 ShortStun，WHEN 巫師於僵直期間再次受到一次離散且傷害 > 0 的攻擊，THEN 該次受擊事件被忽略，`ShortStunDuration` 倒數不重置、不延長（驗證規則13的不可重入）。
21. GIVEN 巫師處於 Windup 的第 0.3 秒那一幀，同時滿足「前搖完成」與「受到攻擊」兩個條件，WHEN 結算該幀，THEN 優先處理受擊，狀態轉為 ShortStun，該幀不生成效果實例（驗證規則8的同幀優先序）。
22. GIVEN 巫師處於 Windup，WHEN 前搖 0.3 秒完整經過未受打斷，THEN 同一幀：①生成一個新的效果實例並進入其 Phase 1、廣播 `OnChainConfirmed` 與 `OnChainPhaseAdvanced(1)` ②該技能同幀由 Ready 轉為 CoolingDown，CD 剩餘 == `ChainSkillCooldown`（±0.001）③全域狀態機回到 Idle、`IsInCastMode()` 轉為 false（驗證規則8：CD 起點與全域狀態機回歸 Idle 為同一幀，不再有矛盾）。
23. GIVEN 技能 A 剛生成效果實例（因而進入 CoolingDown），WHEN 玩家對技能 B（已解鎖、不在 CD、配方滿足）按鍵，THEN **同一幀**技能 B 正常進入 Aiming（**第2輪修訂，行為與原版本相反**：技能 A 的效果實例推進中不再鎖定技能 B 的輸入，因為全域狀態機在技能 A 生成效果實例的同一幀就已回到 Idle，見規則10「不同技能的效果實例允許同時並行」）。
23a. GIVEN 技能 A 的效果實例仍在推進中，WHEN 玩家再次按下技能 A 自己的鍵，THEN 因技能 A 處於 CoolingDown，輸入無效、不進入 Aiming（驗證同一技能不會有兩個效果實例同時存在，規則10）。
24. GIVEN 某技能的效果實例的所有階段依其策略定義正常推進完畢，WHEN 最後階段結束，THEN 廣播 `OnChainCompleted` 恰一次、效果實例參考轉為 null；該技能可用性仍為 `CoolingDown`、CD 剩餘 == `ChainSkillCooldown − 效果實例存活時長`（±1 frame），**不因 `OnChainCompleted` 而歸零或重置**（**第3輪修訂**：原「不受此事件影響」為不可證偽措辭，與第1輪被判不合格的 AC17/18/25 同一個字眼；改為逐項可驗證斷言）。
25. GIVEN 某技能的效果實例因條件未達成（如「星星之火」火種過期或打空）導致階段流程無法自然結束，WHEN 累計時間達到該技能宣告的 `MaxActiveDuration`，THEN 該效果實例強制結束、廣播 `OnChainCompleted` 恰一次，未觸發的階段不補放（驗證規則10的強制退出）；該技能可用性仍為 `CoolingDown`、CD 剩餘 == `ChainSkillCooldown − MaxActiveDuration`（±1 frame），不因強制結束而歸零或重置（**第3輪修訂**：原「不受影響」改為可驗證斷言）。
26. GIVEN 技能處於 CoolingDown，WHEN CD 倒數歸零，THEN 轉為 Ready，可再次通過規則3判定觸發。
27. GIVEN 技能處於 CoolingDown，WHEN 玩家按下該技能鍵，THEN 輸入無效，不進入 Aiming。
28. GIVEN 某技能的效果實例正在推進中，WHEN 巫師受到攻擊，THEN 巫師不進入 ShortStun（全域狀態機此時已在 Idle，可自由進行下一次 Aiming），且該效果實例階段推進的計時與判定不受影響（以與未受擊對照組的階段剩餘時間差值 ≤1 frame 驗證）。

### 落點與逐技能宣告

29. GIVEN 巫師處於 Aiming 狀態，WHEN 玩家的準心移動到 CastCircle 範圍外，THEN 落點回傳座標與圓心距離等於半徑（±0.01），且位於「圓心→準心命中點」的射線上，`IsInCastMode()` 仍為 true，輸入不被拒絕。
30. GIVEN 巫師處於 Aiming 狀態超過 `CastModeDwellBudget`（1.0秒）**且配方持續滿足**（參與塔全數存活並維持原屬性），WHEN 玩家仍未按下左鍵，THEN 至 t=10.0 秒狀態仍為 Aiming，未廣播 `OnChainConfirmed` 或 `OnChainInterrupted`（驗證規則6：`CastModeDwellBudget` 不是計時器，不自動觸發、不自動取消）。
30a. GIVEN 巫師處於 Aiming 狀態，WHEN 於 t=3.0 秒時一座參與塔被拆除（配方因此不再滿足），THEN 同一幀返回 Idle、不進 CD、廣播 `OnChainInterrupted(MaterialInvalidated)` 恰一次（驗證規則7的配方持續重驗；與 AC30 併讀可證「久駐不是免費的，但時間本身不是代價」）。
31. GIVEN 某技能於策略定義宣告「不受 CastCircle 約束」（如星星之火），WHEN 該技能進入 Aiming 且準心指向距巫師 3 倍 `ChainDetectionRadius` 處，THEN 回傳落點等於準心命中點（未被夾取，±0.01）。
32. GIVEN 某技能於策略定義宣告以「快照判定」推進階段（如凍土 Phase 2，t=2.0 時對當下站在領域內的敵人判定），WHEN 累計時間首次 ≥ 2.0 秒，THEN 於該幀的傷害結算階段之後，對距離領域中心 ≤ K（含邊界）的敵人套用定身效果，t=2.0 之後才進入領域的敵人不受影響。
33. GIVEN 某技能於策略定義宣告以「條件觸發」推進階段（如星星之火 Phase 2），WHEN 該條件在該技能的效果實例推進期間達成，THEN 同一幀（≤1 frame）廣播 `OnChainPhaseAdvanced(2)`，不等待固定計時器。
34. GIVEN 巫師在 Aiming 期間鎖定了 CastCircle 快照，WHEN 參與塔隨後被拆除或進入破損狀態，THEN 目前的 Aiming 不被取消，CastCircle 半徑與圓心不回溯改變；WHEN 前搖完成、生成效果實例前重新驗證參與塔，THEN 若驗證失敗（塔已被拆除或寶石被取下），**第2輪修訂**：回到 Idle（無代價取消，不進 ShortStun），不進 CD，不生成效果實例，廣播 `OnChainInterrupted(MaterialInvalidated)`（見 Edge Cases、AC53）。
35. GIVEN 星星之火處於 Aiming 狀態且準心未命中任何敵人的 hit box，WHEN 玩家按下左鍵，THEN 仍正常進入 Windup 並於前搖完成後消耗 CD（與命中時流程相同）；Phase 1 的點燃效果不生效、不產生火種標記，Phase 2 永不觸發；**該技能已於 Windup 完成當幀進入 CoolingDown**，`MaxActiveDuration` 到期時僅廣播 `OnChainCompleted`，CD 剩餘不因此改變（±1 frame）（**第3輪修訂**：原尾句「`MaxActiveDuration` 到期後強制轉入 CoolingDown」與規則8／AC22／AC24 的「CD 於效果實例生成當幀起算」直接衝突——正是 AC24 宣稱已修掉的那個矛盾的殘留）。

### 公式與數值案例

36. GIVEN 任意場上塔配置（含零塔），WHEN 查詢 `ChainDetectionRadius`，THEN 結果恆為 6（±0.001），不受塔的射程或數量影響。

39. GIVEN 三個 MVP 連攜技共用 `ChainSkillCooldown = 30` 秒起點值，WHEN 施放「炎寒領域」後立即查詢「凍土」與「星星之火」的可用性狀態，THEN 兩者皆為 Ready、CD 剩餘皆 == 0（±0.001）（**第2輪修訂**：原「不受影響」改為逐項可驗證斷言，驗證各技能獨立計時）。
40. GIVEN 前搖期間受到攻擊，WHEN 進入 ShortStun，THEN `ShortStunDuration`（1.0 秒）倒數後狀態轉為 Idle，於 t = 1.0 秒（第 60 幀，±1 frame）轉移（**第2輪修訂**：時間類斷言容許值由 ±0.001 改為 ±1 frame，與 AC20 一致；原 ±0.001 對 60 FPS 的幀量化誤差而言不可能通過）。
41. 🚫 GIVEN 火種標記已存在 8 秒（`EmberDuration`）且未被風屬性攻擊觸發，WHEN 第 9 秒風塔命中該敵人，THEN 火種已過期，Phase 2 不觸發引爆（**第2輪修訂**：補標 🚫——「風塔命中」依賴傷害計算系統的「攻擊已結算」回呼，與 AC32/33 同源於 Open Question #4，目前連可信 stub 都寫不出來，`qa-lead` 覆核指出原版本漏標）。
42. GIVEN 已有火種標記的敵人，WHEN 再次施放星星之火 Phase 1 命中，THEN `EmberDuration` 重置為 8 秒，不產生第二個火種疊加。

### 邊界情況延伸

44. ⚠️ GIVEN 「炎寒領域」暴風雪賦予霜屬性，WHEN 火海階段於 t = 4.499 秒對該敵人判定，THEN 套用 `AffinityMult = 1.5`；GIVEN 判定發生於 t = 4.500 秒（**恰好時效終點，不含邊界**），THEN 視為已過期，僅以敵人原生 `BaseAttribute` 計算剋制（可能無剋制）。
44a. GIVEN 「炎寒領域」的階段時長與 `PhaseTickInterval` 為 stub 值，WHEN 列舉火海階段所有判定時點，THEN 最後一次判定時點 ≤ 4.0 秒，恆不觸及 4.5 秒時效邊界（驗證安全邊際確實存在，而非靠邊界含入僥倖成立）。
45. GIVEN 領域效果生效中的敵人在階段中途死亡，WHEN 階段繼續作用，THEN 區域內其餘敵人每次 tick 仍受該階段既定的 `ChainSkillDamage` 判定（±0.001），直到該階段結束。
46. GIVEN 敵人在階段1結束前離開領域範圍後又重新進入（且技能未宣告不同的接觸判定規則），WHEN 重新進入，THEN 視為新的一次接觸判定，`ApplyAttribute` 呼叫次數較上次 +1；GIVEN 敵人在領域邊界附近抖動但從未完全離開範圍，THEN 不重複觸發（驗證「逐來源獨立判定、離開才重置」政策，非「不做去重複判定」）。
47. GIVEN 同一敵人先後被兩個不同連攜領域的階段1賦予不同屬性，WHEN 第二次賦予發生，THEN `AppliedAttribute` 等於第二個屬性且 `AppliedAttributeRemaining` 等於新賦予的時效值（±0.001，時效重新計算而非累加）。
48. GIVEN 凍土定身的敵人，WHEN 受到風塔等擊退類效果，THEN 位置變化量為 0（±0.001），且仍正常受傷害。
49. GIVEN 三個 MVP 連攜技同時皆在 CoolingDown，WHEN 敵人持續來襲，THEN 已嵌合寶石的基礎塔在此 10 秒內的攻擊次數與「連攜可用」對照組相同（±1 次），不因連攜技不可用而停止或降低。
50. GIVEN 巫師處於 Aiming 或 Windup 狀態，WHEN 巫師死亡，THEN 該次施法視為取消，技能不進 CD，全域狀態機轉為 Idle 或由遊戲流程系統接管。
51. GIVEN 巫師已有效果實例在推進中（領域/標記已生成），WHEN 巫師於此時死亡，THEN 已生成的效果依既定規則繼續作用至自然結束或 `MaxActiveDuration` 到期，但不再推進尚未觸發的後續階段；該技能 CD 於巫師死亡後第 1 幀與第 60 幀量測，皆與「巫師未死亡對照組」同幀值相等（±1 frame）（**第3輪修訂**：原「不受影響」改為可驗證斷言）。

### 事件廣播

52. GIVEN 完整流程從按鍵到效果實例生成，WHEN 依序經過 Aiming／Windup／效果實例生成 各轉移，THEN 依序廣播 `OnChainAiming`、`OnChainConfirmed`、`OnChainPhaseAdvanced`（每個階段各一次）、`OnChainCompleted`（最後階段結束或 `MaxActiveDuration` 強制結束時各一次）。
53. GIVEN Aiming 中，WHEN 移動軸超過死區，THEN 廣播 `OnChainInterrupted` 恰一次且 `reason == MovementCancel`。
53a. GIVEN Aiming 中，WHEN 受到一次離散且傷害 > 0 的攻擊，THEN 廣播恰一次且 `reason == HitCancel`。
53b. GIVEN Windup 中，WHEN 受擊，THEN 廣播恰一次且 `reason == WindupInterrupted`。
53c. GIVEN Aiming 中配方不再滿足（規則7）**或** Windup 完成當幀重驗參與塔失敗，WHEN 中止發生，THEN 廣播恰一次、`reason == MaterialInvalidated`、該技能 CD 剩餘 == 0，**且事件 payload 攜帶失效的塔實例 ID**（第3輪新增：齊頭式「參與塔高亮消散」只讓玩家知道「有材料沒了」卻不知道是哪一座，而「那座火塔被拆了」才是可行動資訊，見 Visual/Audio Requirements）。
53d. GIVEN 上述四個情境各執行一次，THEN 四者的 `reason` 值兩兩相異，且任一情境下 `OnChainInterrupted` 廣播次數恰為 1（**第3輪修訂**：原 AC53 把四個觸發條件打包在同一個 GIVEN、THEN 只說「可供訂閱方區分」——一個永遠回傳 `MovementCancel` 的實作可以通過寬鬆解讀）。
53e. GIVEN 一個 mock 動畫／VFX 訂閱者，WHEN 依序觸發五種結束態（含 `Preempted`），THEN 收到的表現語言 id 恰為**三個相異值**（無代價取消／踉蹌／換檔），其中 `MovementCancel`、`HitCancel`、`MaterialInvalidated` 對應同一個值，`WindupInterrupted` 與 `Preempted` 各自獨立（驗證第3輪的語言收斂，見 Visual/Audio Requirements）（**第2輪修訂**：原三種擴為四種，新增「材料失效」，見 Edge Cases／AC34；呼應 Visual/Audio Requirements 的語言互異需求——`MaterialInvalidated` 須有獨立於 `WindupInterrupted` 踉蹌動作的視覺語言，因為玩家在此情境下完全沒有被打，不應誤判為「我被打了」）。
54. GIVEN 巫師處於 Aiming 中被另一技能搶佔（規則2），WHEN 搶佔發生，THEN 廣播 `OnChainInterrupted(Preempted)`（**第2輪修訂新增**：搶佔亦須廣播可區分的原因，供 UI／VFX 播放「換檔」而非「取消」語言，見 Visual/Audio Requirements）。
54a. GIVEN 完整流程執行，WHEN 全程監控巫師 Transform 的 setter 呼叫，THEN 連攜系統本身未寫入巫師 Transform（以 mock 巫師驗證，呼叫次數 == 0，驗證 systems-index §3③ 的單向依賴架構保證）。

### 效能
